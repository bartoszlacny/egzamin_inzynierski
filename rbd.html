Relacyjne bazy danych

1. Normalizacja

Proces organizowania danych w tabelach tak, by zminimalizować redundancję (powtarzanie się danych) i uniknąć anomalii (problemów przy wstawianiu, aktualizacji, usuwaniu danych).

Anomalie (problem, który normalizacja rozwiązuje)

  • anomalia wstawiania — nie można wprowadzić pewnych danych bez wprowadzenia innych, niepowiązanych logicznie
  • anomalia usuwania — usunięcie wiersza niechcący usuwa też inną, wciąż potrzebną informację
  • anomalia aktualizacji — ta sama informacja powtórzona w wielu wierszach — trzeba zmienić wszystkie kopie, inaczej dane staną się niekonsystentne

Pierwsza postać normalna (1NF)

  • każda kolumna zawiera wartości atomowe (niepodzielne) — nie listy, nie wielokrotne wartości w jednej komórce
  • brak powtarzających się grup kolumn (np. telefon1, telefon2, telefon3 — powinno być osobną tabelą)

Druga postać normalna (2NF)

Tabela jest w 1NF i każdy atrybut niekluczowy zależy od całego klucza głównego (nie tylko od jego części) — istotne przy kluczach złożonych (z wielu kolumn).

Trzecia postać normalna (3NF)

Tabela jest w 2NF i brak zależności przechodnich — atrybut niekluczowy nie może zależeć od innego atrybutu niekluczowego, tylko wyłącznie od klucza głównego.

Przykład — od tabeli niesznormalizowanej do 3NF

-- Zła struktura (dane zamówień z powtórzoną nazwą klienta i miasta)
Zamowienie(id_zam, produkt, klient, miasto_klienta, cena)

-- 3NF: rozbicie na osobne tabele
Klient(id_klient, nazwa, miasto)
Zamowienie(id_zam, id_klient, produkt, cena)

W wersji 3NF zmiana miasta klienta wymaga edycji jednego wiersza w Klient, a nie każdego zamówienia tego klienta.

Wyższe postacie normalne (skrótowo)

BCNF (postać normalna Boyce'a-Codda) — mocniejsza wersja 3NF; 4NF, 5NF — dotyczą rzadszych, bardziej złożonych zależności — w praktyce projektowania baz danych zwykle wystarcza dojście do 3NF/BCNF.

Kompromis: pełna normalizacja minimalizuje redundancję, ale zwiększa liczbę tabel i konieczność złączeń (JOIN) przy odczycie — czasem świadomie stosuje się denormalizację (częściowe scalenie danych) dla wydajności odczytu w systemach o bardzo dużym obciążeniu read-heavy.

2. Diagramy ERD (Entity-Relationship Diagram)

Graficzny sposób modelowania struktury bazy danych przed jej implementacją — pokazuje encje (przyszłe tabele), ich atrybuty i relacje między nimi.

Podstawowe elementy

  • encja (entity) — obiekt/koncept, o którym przechowujemy dane (np. Klient, Produkt) — w implementacji staje się tabelą
  • atrybut — właściwość encji (np. imię, cena) — staje się kolumną
  • klucz główny (primary key, PK) — atrybut(y) jednoznacznie identyfikujące wiersz encji
  • relacja (związek) — powiązanie między encjami (np. Klient składa Zamówienie)

Liczebność (kardynalność) relacji

TypOpisPrzykład
1:1 (jeden do jednego)jeden wiersz A odpowiada max. jednemu wierszowi BOsoba — Paszport
1:N (jeden do wielu)jeden wiersz A może odpowiadać wielu wierszom BKlient — Zamówienia
N:M (wiele do wielu)wiele wierszy A może odpowiadać wielu wierszom BStudenci — Kursy

Notacja "kurzej łapki" (crow's foot)

Popularny sposób rysowania kardynalności na diagramie — symbole na końcach linii łączącej encje wskazują minimalną i maksymalną liczbę wystąpień (np. "rozdwojona łapka" = "wiele", pojedyncza kreska = "jeden", okrąg = "zero lub...").

Relacja N:M w implementacji

Relacja wiele-do-wielu nie może być bezpośrednio zapisana kluczem obcym w jednej z tabel — wymaga tabeli łączącej (pośredniej) z kluczami obcymi do obu tabel (patrz punkt 5).

Od ERD do schematu tabel

  1. każda encja → tabela
  2. każdy atrybut → kolumna
  3. relacja 1:N → klucz obcy w tabeli po stronie "wiele"
  4. relacja N:M → dodatkowa tabela łącząca z dwoma kluczami obcymi
Typowe zadanie: narysuj diagram ERD dla opisanego słownie systemu (np. "sklep internetowy: klienci składają zamówienia, zamówienie zawiera wiele produktów") i przetłumacz go na konkretny schemat tabel z kluczami głównymi/obcymi.

3. Zapytania SQL — DDL, DML, DQL

DDL (Data Definition Language) — definicja struktury

CREATE TABLE Klient (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nazwa VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE
);

ALTER TABLE Klient ADD COLUMN telefon VARCHAR(20);
DROP TABLE Klient;

Polecenia: CREATE, ALTER, DROP, TRUNCATE — tworzą/modyfikują/usuwają strukturę bazy (tabele, indeksy, ograniczenia), nie same dane.

DML (Data Manipulation Language) — manipulacja danymi

INSERT INTO Klient (nazwa, email) VALUES ('Jan Kowalski', 'jan@example.com');

UPDATE Klient SET email = 'nowy@example.com' WHERE id = 1;

DELETE FROM Klient WHERE id = 1;

Polecenia: INSERT, UPDATE, DELETE — dodają, modyfikują, usuwają wiersze danych (struktura tabeli bez zmian).

DQL (Data Query Language) — odczyt danych

SELECT nazwa, email FROM Klient WHERE id > 5 ORDER BY nazwa;

SELECT — jedyne polecenie DQL, ale z bardzo bogatą składnią (WHERE, ORDER BY, GROUP BY, JOIN, patrz punkty 4-5).

Inne kategorie (dla kompletności)

KategoriaPoleceniaCel
DCL (Data Control Language)GRANT, REVOKEzarządzanie uprawnieniami użytkowników
TCL (Transaction Control Language)COMMIT, ROLLBACK, SAVEPOINTzarządzanie transakcjami

Klucze i ograniczenia (constraints)

CREATE TABLE Zamowienie (
    id INT PRIMARY KEY,
    id_klient INT,
    data DATE NOT NULL,
    FOREIGN KEY (id_klient) REFERENCES Klient(id)
);
  • PRIMARY KEY — jednoznaczny identyfikator wiersza
  • FOREIGN KEY — odwołanie do klucza głównego innej tabeli, wymuszające integralność referencyjną
  • NOT NULL, UNIQUE, CHECK — dodatkowe ograniczenia wartości kolumny
Typowe pytanie: rozróżnij, czy dane polecenie SQL to DDL, DML czy DQL — klasyczna, szybka pytanie sprawdzające, czy rozumiesz podział na definicję struktury vs manipulację danymi vs odczyt.

4. Funkcje agregujące

Funkcje operujące na zbiorze wierszy, zwracające jedną wartość podsumowującą — kluczowe przy analizie/raportowaniu danych.

FunkcjaDziałanie
COUNT(*)liczba wierszy
COUNT(kolumna)liczba wierszy z niepustą (NOT NULL) wartością w kolumnie
SUM(kolumna)suma wartości
AVG(kolumna)wartość średnia
MIN(kolumna) / MAX(kolumna)wartość minimalna/maksymalna

GROUP BY — agregacja w grupach

SELECT id_klient, COUNT(*) AS liczba_zamowien, SUM(cena) AS suma
FROM Zamowienie
GROUP BY id_klient;

Dzieli wiersze na grupy według wartości podanej kolumny, i liczy funkcję agregującą osobno dla każdej grupy (nie dla całej tabeli naraz).

HAVING — filtrowanie grup (nie pojedynczych wierszy!)

SELECT id_klient, SUM(cena) AS suma
FROM Zamowienie
GROUP BY id_klient
HAVING SUM(cena) > 1000;

Różnica WHERE vs HAVING

WHEREHAVING
Filtrujepojedyncze wiersze, PRZED grupowaniemgrupy (wyniki agregacji), PO grupowaniu
Może użyć funkcji agregującej?nietak

Kolejność wykonania zapytania (koncepcyjnie)

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY — istotne, żeby zrozumieć, dlaczego WHERE nie może odwołać się do wyniku agregacji (jeszcze nie istnieje w tym momencie wykonania).

Klasyczny błąd: próba użycia funkcji agregującej w WHERE (WHERE COUNT(*) > 5) — to zawsze błąd składniowy, poprawnie trzeba użyć HAVING.

5. Typy relacji, zapytania SELECT na wielu tabelach

Relacja 1:N w implementacji

CREATE TABLE Klient (id INT PRIMARY KEY, nazwa VARCHAR(50));
CREATE TABLE Zamowienie (
    id INT PRIMARY KEY,
    id_klient INT,
    FOREIGN KEY (id_klient) REFERENCES Klient(id)
);

Klucz obcy (id_klient) umieszczony w tabeli po stronie "wiele" (Zamówienie) — jeden klient może mieć wiele zamówień.

Relacja N:M — tabela łącząca

CREATE TABLE Student (id INT PRIMARY KEY, nazwa VARCHAR(50));
CREATE TABLE Kurs (id INT PRIMARY KEY, tytul VARCHAR(50));
CREATE TABLE Student_Kurs (
    id_student INT,
    id_kurs INT,
    PRIMARY KEY (id_student, id_kurs),
    FOREIGN KEY (id_student) REFERENCES Student(id),
    FOREIGN KEY (id_kurs) REFERENCES Kurs(id)
);

Typy złączeń (JOIN)

JOINZasada
INNER JOIN tylko wiersze mające dopasowanie w obu tabelach
LEFT JOIN wszystkie wiersze z lewej tabeli + dopasowane z prawej (NULL, jeśli brak dopasowania)
RIGHT JOIN wszystkie wiersze z prawej tabeli + dopasowane z lewej
FULL OUTER JOIN wszystkie wiersze z obu tabel, dopasowane gdzie możliwe, NULL gdzie brak dopasowania

Przykład — INNER JOIN

SELECT k.nazwa, z.data, z.cena
FROM Klient k
INNER JOIN Zamowienie z ON k.id = z.id_klient;

Przykład — złączenie przez tabelę łączącą (N:M)

SELECT s.nazwa, k.tytul
FROM Student s
JOIN Student_Kurs sk ON s.id = sk.id_student
JOIN Kurs k ON k.id = sk.id_kurs;

Przykład — LEFT JOIN (klienci nawet bez zamówień)

SELECT k.nazwa, COUNT(z.id) AS liczba_zamowien
FROM Klient k
LEFT JOIN Zamowienie z ON k.id = z.id_klient
GROUP BY k.nazwa;

W odróżnieniu od INNER JOIN, klient bez żadnego zamówienia wciąż pojawi się w wyniku (z liczba_zamowien = 0).

Podzapytania (subqueries)

SELECT nazwa FROM Klient
WHERE id IN (SELECT id_klient FROM Zamowienie WHERE cena > 1000);

Zapytanie zagnieżdżone w innym zapytaniu — alternatywa (czasem bardziej czytelna, czasem mniej efektywna) dla JOIN, w zależności od sytuacji.

Typowe zadanie: napisz zapytanie SQL wymagające złączenia 2-3 tabel z funkcją agregującą i grupowaniem naraz (np. "znajdź klientów, którzy złożyli więcej niż 3 zamówienia, wraz z sumą wydanych pieniędzy") — łączy w sobie punkty 3, 4 i 5.

6. Transakcje i własności ACID

Transakcja — sekwencja operacji na bazie danych traktowana jako jedna, niepodzielna jednostka pracy — albo wykonuje się w całości, albo w ogóle (jeśli coś pójdzie źle, wszystkie zmiany są wycofywane).

Podstawowe polecenia

BEGIN TRANSACTION;

UPDATE Konto SET saldo = saldo - 100 WHERE id = 1;
UPDATE Konto SET saldo = saldo + 100 WHERE id = 2;

COMMIT;   -- zatwierdzenie wszystkich zmian na trwałe
-- albo:
ROLLBACK; -- wycofanie wszystkich zmian od BEGIN TRANSACTION

Własności ACID

WłaściwośćZnaczenie
Atomicity (atomowość) transakcja wykonuje się w całości albo wcale — np. przy przelewie między kontami, nie może zajść sytuacja, że pieniądze zostały odjęte z jednego konta, a nie dodane do drugiego (awaria w połowie transakcji)
Consistency (spójność) transakcja przenosi bazę z jednego poprawnego (zgodnego z ograniczeniami — kluczami, constraintami) stanu do innego poprawnego stanu
Isolation (izolacja) równocześnie wykonywane transakcje nie "widzą" swoich niedokończonych, częściowych zmian — każda zachowuje się, jakby była jedyną transakcją w systemie (poziom izolacji określa, jak dokładnie to jest zagwarantowane, patrz niżej)
Durability (trwałość) po COMMIT, zmiany są trwałe — przetrwają nawet awarię zasilania/systemu bezpośrednio po zatwierdzeniu

Poziomy izolacji transakcji

PoziomDopuszczalne anomalie
Read Uncommitteddirty read (odczyt niezatwierdzonych zmian innej transakcji)
Read Committedbrak dirty read, ale możliwy non-repeatable read (ten sam odczyt w tej samej transakcji daje różne wyniki)
Repeatable Readbrak non-repeatable read, ale możliwy phantom read (nowe wiersze pojawiające się między odczytami)
Serializablenajwyższy poziom — transakcje zachowują się, jakby wykonywały się całkowicie po kolei (szeregowo), zero anomalii

Wyższy poziom izolacji = mniej anomalii, ale mniejsza przepustowość (więcej blokad/oczekiwania między transakcjami) — kompromis do wyboru zależnie od wymagań aplikacji.

Klasyczny przykład atomowości: przelew bankowy jako transakcja — UPDATE odejmujący z konta A i UPDATE dodający na konto B muszą być w jednej transakcji, inaczej awaria między nimi zniszczyłaby pieniądze albo je "zduplikowała".

7. Indeksy

Dodatkowa struktura danych (najczęściej B-drzewo — patrz przedmiot Algorytmy i struktury danych) przyspieszająca wyszukiwanie wierszy po wartości danej kolumny, bez potrzeby przeglądania (full table scan) całej tabeli.

Bez indeksu vs z indeksem

Bez indeksuZ indeksem
Wyszukiwanie po kolumnie\(O(n)\) — przegląd całej tabeli\(O(\log n)\) — przeszukanie B-drzewa
Koszt zapisu (INSERT/UPDATE/DELETE)brak dodatkowego narzututrzeba dodatkowo aktualizować strukturę indeksu
Zużycie pamięci/dyskubrak dodatkowegoindeks zajmuje dodatkową przestrzeń

Tworzenie indeksu

CREATE INDEX idx_klient_email ON Klient(email);
CREATE UNIQUE INDEX idx_klient_email ON Klient(email);  -- dodatkowo wymusza unikalność

Klucz główny (PRIMARY KEY) i zwykle też FOREIGN KEY/UNIQUE mają indeks tworzony automatycznie przez silnik bazy danych.

Kiedy stosować indeks

  • kolumny często używane w WHERE, JOIN ... ON, ORDER BY
  • kolumny z dużą selektywnością (wiele różnych wartości) — indeks na kolumnie z tylko dwiema możliwymi wartościami (np. boolean) rzadko pomaga

Kiedy indeks szkodzi / nie pomaga

  • tabele z bardzo częstymi zapisami (INSERT/UPDATE/DELETE) — każdy zapis musi też zaktualizować wszystkie indeksy na danej tabeli, co spowalnia operacje zapisu
  • małe tabele — pełny przegląd małej tabeli i tak jest szybki, narzut indeksu się nie opłaca
  • kolumny o niskiej selektywności (patrz wyżej)

Indeks złożony (na wielu kolumnach)

CREATE INDEX idx_zam_klient_data ON Zamowienie(id_klient, data);

Przydatny dla zapytań filtrujących/sortujących po obu kolumnach naraz (lub tylko po pierwszej z nich) — kolejność kolumn w definicji indeksu ma znaczenie dla tego, jakie zapytania skorzystają z niego efektywnie.

Typowe pytanie: dlaczego nie warto indeksować "wszystkiego" — bo każdy indeks kosztuje przy zapisie (aktualizacja struktury) i zajmuje dodatkową przestrzeń, więc trzeba wybierać kolumny, na których zapytania faktycznie filtrują/sortują/łączą najczęściej.
