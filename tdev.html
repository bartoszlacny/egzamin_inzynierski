Technologie DevOps

1. System kontroli wersji Git

Rozproszony system kontroli wersji (DVCS)

W odróżnieniu od scentralizowanych systemów (np. starszy SVN), każdy klon repozytorium Git zawiera pełną historię projektu — praca lokalna (commity, przeglądanie historii) nie wymaga połączenia z serwerem centralnym, synchronizacja ze zdalnym repozytorium odbywa się jawnie i tylko wtedy, gdy potrzebna.

Commit

Zatwierdzony "zrzut" stanu projektu w danym momencie — zawiera zmiany względem poprzedniego commita, autora, datę, komunikat opisujący zmianę, i wskaźnik (hash) na commit rodzica (rodziców, przy scaleniu branchy).

git add plik.txt          # zaznacz zmiany do commita (staging area)
git commit -m "Opis zmiany"
git log                    # historia commitów

Branch (rozgałęzienie)

Niezależna linia rozwoju kodu — pozwala pracować równolegle nad różnymi funkcjami/poprawkami bez wzajemnego zakłócania się, aż do momentu scalenia zmian.

git branch nowa-funkcja        # utwórz branch
git checkout nowa-funkcja       # przełącz się na branch (albo: git switch nowa-funkcja)
git checkout -b nowa-funkcja    # utwórz i przełącz jednocześnie

git merge nowa-funkcja          # scal zmiany z branchem aktualnym

Konflikty scalania (merge conflicts)

Gdy dwa branche zmieniły ten sam fragment pliku w różny sposób — Git nie jest w stanie automatycznie zdecydować, która wersja jest poprawna, i wymaga ręcznego rozstrzygnięcia przez programistę (zaznaczone w pliku znacznikami <<<<<<<, =======, >>>>>>>).

Praca ze zdalnym repozytorium

git clone https://github.com/user/projekt.git   # skopiowanie zdalnego repo lokalnie
git remote -v                                     # lista zdalnych repozytoriów

git pull                    # pobierz i scal zmiany ze zdalnego repo (fetch + merge)
git push                    # wyślij lokalne commity do zdalnego repo
git fetch                   # pobierz zmiany, ale bez automatycznego scalania

Pull Request / Merge Request

Mechanizm (na platformach jak GitHub/GitLab, nie sam Git) do proponowania scalenia zmian z jednego brancha do innego, z możliwością code review (komentowania, dyskusji) przed faktycznym scaleniem — kluczowy element pracy zespołowej i podstawa procesów CI/CD (patrz punkt 4).

Rebase vs merge (skrótowo)

merge — łączy historie branchy, zachowując oba "wątki" i tworząc commit scalający; rebase — "przenosi" commity jednego brancha na wierzchołek drugiego, tworząc liniową, "czystszą" historię (kosztem przepisania hashy commitów).

Typowe pytanie: opisz typowy workflow pracy zespołowej z Gitem — nowy branch dla funkcji, commity, push do zdalnego repo, pull request, code review, merge do głównego brancha (main/master).

2. Docker — idea konteneryzacji

(pełne porównanie z maszynami wirtualnymi — patrz przedmiot Administracja i integracja systemów operacyjnych)

Idea konteneryzacji

Pakowanie aplikacji wraz z jej zależnościami (biblioteki, konfiguracja, runtime) w izolowaną jednostkę (kontener) — kontenery współdzielą jądro systemu-hosta, ale mają odizolowany od siebie system plików, procesy, sieć.

Obraz (image) vs kontener

docker build -t mojaapp:1.0 .    # zbuduj obraz na podstawie Dockerfile w bieżącym katalogu
docker run mojaapp:1.0            # uruchom kontener z obrazu

Obraz — statyczny, niemutowalny "szablon"; kontener — działająca instancja obrazu (można uruchomić wiele kontenerów z jednego obrazu).

Dockerfile — przykład

FROM python:3.12-slim         # obraz bazowy
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]      # domyślna komenda przy starcie kontenera

Każda instrukcja tworzy nową warstwę (layer) obrazu — warstwy są cache'owane, więc niezmienione warstwy nie muszą być przebudowywane przy kolejnych docker build (stąd zasada: instrukcje rzadziej zmieniające się, np. instalacja zależności, na początku Dockerfile).

Zalety konteneryzacji

  • przenośność — "działa tam samo" niezależnie od hosta (dev/test/produkcja) — eliminuje klasyczny problem "u mnie działało"
  • lekkość — mniejsze zużycie zasobów i szybszy start niż maszyny wirtualne (brak własnego kernela)
  • izolacja zależności — różne aplikacje na tym samym hoście mogą używać różnych (nawet konfliktujących) wersji bibliotek/runtime
  • skalowalność — łatwe uruchamianie wielu identycznych instancji (np. pod load balancerem)
  • powtarzalność — środowisko zdefiniowane jako kod (Dockerfile), wersjonowane w Git

Wady konteneryzacji

  • słabsza izolacja niż maszyny wirtualne (współdzielone jądro — potencjalnie większa powierzchnia ataku między kontenerami niż między VM)
  • nie da się uruchomić kontenera innego systemu operacyjnego niż host (np. kontener Linux wymaga hosta z jądrem Linux)
  • zarządzanie stanem/danymi trwałymi wymaga dodatkowego mechanizmu (wolumeny, patrz punkt 3) — kontenery z natury są efemeryczne
  • dodatkowa złożoność narzędziowa (orkiestracja, sieci, rejestry obrazów) przy większej skali
Typowe pytanie: dla opisanego scenariusza (np. "aplikacja webowa z bazą danych, do wdrożenia na wielu środowiskach") uzasadnij wybór konteneryzacji względem tradycyjnej instalacji na serwerze, wskazując konkretne zalety istotne dla tego przypadku.

3. Docker Compose i sieci Dockerowe

Docker Compose — idea

Narzędzie do definiowania i zarządzania wieloma powiązanymi kontenerami jako jedną, spójną aplikacją — konfiguracja w jednym pliku YAML, zamiast wielu osobnych, długich komend docker run.

Przykładowy docker-compose.yml

version: "3.8"
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      - db
    environment:
      - DB_HOST=db

  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=tajne
    volumes:
      - dane_db:/var/lib/postgresql/data

volumes:
  dane_db:
docker-compose up -d      # zbuduj/uruchom wszystkie usługi w tle
docker-compose down       # zatrzymaj i usuń kontenery
docker-compose logs web   # logi konkretnej usługi

Kluczowe elementy konfiguracji

  • services — definicja poszczególnych kontenerów (aplikacja, baza danych, cache itd.)
  • depends_on — kolejność startu kontenerów (uwaga: nie gwarantuje, że zależna usługa jest już w pełni gotowa, tylko że kontener wystartował)
  • volumes — trwałe przechowywanie danych poza cyklem życia kontenera (patrz niżej)
  • environment — zmienne środowiskowe konfigurujące zachowanie kontenera

Wolumeny (volumes)

Mechanizm trwałego przechowywania danych, niezależny od cyklu życia kontenera — bez wolumenu, usunięcie kontenera (np. bazy danych) usuwa też wszystkie dane wewnątrz niego.

Sieci Dockerowe

Docker automatycznie tworzy izolowaną sieć dla usług zdefiniowanych w jednym docker-compose.yml — kontenery mogą się komunikować między sobą po nazwie usługi (jak DNS wewnątrz tej sieci), np. web łączy się z bazą po adresie db, bez potrzeby znać jej faktyczny adres IP.

Typ sieciZasada
Bridge (domyślna)izolowana sieć wirtualna na hoście — kontenery w tej samej sieci bridge widzą się nawzajem
Hostkontener współdzieli sieć hosta bezpośrednio (brak izolacji sieciowej)
Overlaysieć rozciągnięta między wieloma hostami (np. w klastrze Docker Swarm/Kubernetes)
Typowe pytanie: zaprojektuj docker-compose.yml dla aplikacji webowej z bazą danych i cache (np. Redis), z odpowiednim mapowaniem portów i wolumenem dla trwałości danych bazy.

4. CI/CD z GitHub Actions

CI (Continuous Integration)

Praktyka częstego integrowania zmian kodu do głównego brancha, z automatycznym uruchamianiem testów przy każdej zmianie — pozwala wcześnie wykrywać konflikty/błędy, zamiast odkrywać je po tygodniach osobnej pracy wielu deweloperów.

CD (Continuous Delivery / Deployment)

Delivery — kod po przejściu testów jest automatycznie przygotowany do wdrożenia (ale wdrożenie na produkcję wymaga jeszcze ręcznej akceptacji); Deployment — pełna automatyzacja, kod przechodzący testy trafia na produkcję bez ręcznej interwencji.

GitHub Actions — podstawy

Mechanizm automatyzacji wbudowany w GitHub — definiowany plikami YAML w katalogu .github/workflows/, reagujący na zdarzenia w repozytorium (push, pull request, itd.).

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # pobranie kodu repozytorium
      - name: Ustaw Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Zainstaluj zależności
        run: pip install -r requirements.txt
      - name: Uruchom testy
        run: pytest

Kluczowe pojęcia workflow

ElementZnaczenie
onzdarzenie wyzwalające workflow (push, pull_request, harmonogram cron, ręczne wywołanie)
jobsniezależne (domyślnie równoległe) zadania, każde na własnym, czystym środowisku (runner)
stepssekwencja kroków wewnątrz jednego joba, wykonywana po kolei
usesodwołanie do gotowej, współdzielonej akcji (np. checkout kodu, setup środowiska)
runbezpośrednie wykonanie komendy powłoki

Rozszerzenie o CD — automatyczny deployment

  deploy:
    needs: test              # deploy tylko jeśli job "test" się powiódł
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - name: Zbuduj i wypchnij obraz Docker
        run: |
          docker build -t mojaapp:${{ github.sha }} .
          docker push mojaapp:${{ github.sha }}
      - name: Wdróż na serwer
        run: ssh serwer "docker pull mojaapp:${{ github.sha }} && docker-compose up -d"

Secrets

Wrażliwe dane (klucze API, hasła, tokeny SSH) przechowywane w bezpiecznym magazynie GitHub (Settings → Secrets), dostępne w workflow jako ${{ secrets.NAZWA }} — nigdy nie wpisywane wprost w pliku YAML (byłyby widoczne w historii repozytorium).

Typowe pytanie: zaprojektuj pipeline CI/CD dla prostej aplikacji webowej — testy jednostkowe przy każdym pull request, automatyczny build i deployment obrazu Docker na serwer po scaleniu do brancha main.

5. Monitorowanie — Prometheus i Grafana

Prometheus — zbieranie metryk

System monitoringu działający na zasadzie pull — Prometheus okresowo odpytuje (scrape) endpointy monitorowanych aplikacji o aktualne metryki (w odróżnieniu od modelu push, gdzie aplikacje same wysyłają dane do systemu monitorującego).

Model danych — szeregi czasowe

Metryki przechowywane jako szeregi czasowe (wartość + znacznik czasu + etykiety/labels), np.:

http_requests_total{method="GET", status="200"} 15230
cpu_usage_percent{host="serwer1"} 45.2

PromQL — język zapytań

rate(http_requests_total[5m])              # tempo żądań na sekundę, w oknie 5 minut
avg(cpu_usage_percent) by (host)             # średnie zużycie CPU per host

Grafana — wizualizacja

Narzędzie do budowania dashboardów (paneli z wykresami/tabelami) na podstawie danych z różnych źródeł (Prometheus i wiele innych) — Prometheus zbiera i przechowuje dane, Grafana je prezentuje w czytelnej, konfigurowalnej formie.

Alerting

Zarówno Prometheus (Alertmanager) jak i Grafana pozwalają definiować reguły alarmowe — np. "powiadom, gdy CPU > 90% przez ponad 5 minut" — z wysyłką powiadomień (e-mail, Slack, PagerDuty) do zespołu.

Zalety Prometheus + Grafana

ZaletyWady
open-source, bardzo popularny standard w świecie DevOps/KubernetesPrometheus domyślnie przechowuje dane lokalnie — skalowanie do bardzo długiej retencji/wielu klastrów wymaga dodatkowych rozwiązań (np. Thanos, Cortex)
elastyczny model etykiet (labels) — łatwe filtrowanie/agregacja wg wielu wymiarówmodel pull wymaga, by monitorowane aplikacje były "dostępne" dla Prometheusa (utrudnione dla krótko żyjących zadań — wymaga Pushgateway)
duża biblioteka gotowych "exporterów" (dla baz danych, serwerów WWW, systemów operacyjnych)PromQL ma pewną krzywą uczenia, mniej intuicyjny niż prosty SQL dla początkujących
Grafana wspiera wiele źródeł danych naraz, nie tylko Prometheuspełne wdrożenie (alerting, długa retencja, HA) wymaga dodatkowej konfiguracji/komponentów

Typowy stack monitoringu

Aplikacja (eksponuje metryki na /metrics) → Prometheus (scrape + przechowywanie) → Grafana (dashboard) 
                                                     ↓
                                              Alertmanager (powiadomienia)
Typowe pytanie: wyjaśnij różnicę między rolą Prometheusa i Grafany w typowym stacku monitoringu — Prometheus zbiera i przechowuje metryki (i może alarmować), Grafana służy głównie do wizualizacji (może korzystać też z innych źródeł danych niż Prometheus).

6. Infrastructure as Code (Terraform, Ansible)

Idea zarządzania infrastrukturą (serwery, sieci, bazy danych w chmurze) przez kod (pliki konfiguracyjne wersjonowane w Git), a nie ręczne klikanie w panelach administracyjnych — infrastruktura staje się powtarzalna, wersjonowana i przeglądalna jak każdy inny kod.

Deklaratywne vs imperatywne podejście

Deklaratywne (np. Terraform)Imperatywne (np. skrypty bash, częściowo Ansible)
Opisujejaki powinien być stan końcowyjakie kroki wykonać, żeby go osiągnąć
Idempotencjanaturalna — narzędzie sam wyznacza różnicę i potrzebne zmianytrzeba samemu zapewnić (żeby ponowne uruchomienie nie zaszkodziło)

Terraform — provisioning infrastruktury

resource "aws_instance" "serwer_web" {
  ami           = "ami-0123456789"
  instance_type = "t3.micro"

  tags = {
    Name = "serwer-produkcyjny"
  }
}
terraform init      # inicjalizacja (pobranie dostawców/providers)
terraform plan       # pokaż, co się zmieni (bez wykonywania zmian)
terraform apply      # zastosuj zmiany — utwórz/zmodyfikuj rzeczywistą infrastrukturę

Terraform śledzi stan (state) rzeczywistej infrastruktury i porównuje go z opisem docelowym — plan pokazuje różnicę przed wprowadzeniem zmian, co minimalizuje ryzyko przypadkowych, nieprzewidzianych modyfikacji.

Ansible — konfiguracja i automatyzacja

Narzędzie do konfigurowania już istniejących serwerów (instalacja pakietów, konfiguracja usług, deployment aplikacji) — działa przez SSH, bez agenta instalowanego na zarządzanych maszynach (w odróżnieniu np. od Puppet/Chef).

# playbook.yml
- hosts: serwery_web
  tasks:
    - name: Zainstaluj nginx
      apt:
        name: nginx
        state: present
    - name: Uruchom usługę nginx
      service:
        name: nginx
        state: started
ansible-playbook -i inventory.ini playbook.yml

Terraform vs Ansible — uzupełniające się role

TerraformAnsible
Główne zastosowanietworzenie infrastruktury (serwery, sieci, bazy danych w chmurze)konfiguracja tego, co już istnieje (pakiety, usługi, pliki konfiguracyjne)
Typowy przepływTerraform tworzy serwer → Ansible konfiguruje na nim oprogramowanie — często używane razem, nie zamiennie
Typowe pytanie: wyjaśnij, dlaczego "ręczne" konfigurowanie serwerów przez SSH ("click-ops") jest problematyczne w większych zespołach/projektach, i jak IaC (Terraform/Ansible) rozwiązuje te problemy (powtarzalność, wersjonowanie, code review dla zmian infrastruktury).

7. Kubernetes — orkiestracja kontenerów

Rozwinięcie problemu z punktu 3 (Docker Compose) na dużą skalę — Docker Compose dobrze zarządza kontenerami na jednej maszynie, Kubernetes orkiestruje kontenery rozproszone na wielu maszynach (klaster), z automatycznym skalowaniem i samonaprawą.

Podstawowe pojęcia

PojęcieOpis
Podnajmniejsza jednostka wdrożenia — jeden lub kilka ściśle powiązanych kontenerów, współdzielących sieć/wolumeny
Nodefizyczna/wirtualna maszyna w klastrze, na której działają Pody
Deploymentdeklaratywny opis, ile replik danego Poda powinno działać i jak je aktualizować
Servicestabilny punkt dostępu (adres/nazwa) do grupy Podów — Pody są efemeryczne (mogą być tworzone/usuwane), Service daje trwały "adres" niezależny od konkretnych instancji
Namespacelogiczny podział klastra (np. na środowiska dev/test/prod, albo różne zespoły)

Przykładowy manifest Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: mojaapp
spec:
  replicas: 3                     # 3 identyczne kopie (repliki) aplikacji
  selector:
    matchLabels:
      app: mojaapp
  template:
    metadata:
      labels:
        app: mojaapp
    spec:
      containers:
        - name: mojaapp
          image: mojaapp:1.0
          ports:
            - containerPort: 80
kubectl apply -f deployment.yaml
kubectl get pods
kubectl scale deployment mojaapp --replicas=5

Kluczowe funkcjonalności

  • automatyczne skalowanie — zwiększanie/zmniejszanie liczby replik wg obciążenia (Horizontal Pod Autoscaler)
  • samonaprawa (self-healing) — jeśli Pod "padnie" albo przestanie odpowiadać, Kubernetes automatycznie tworzy nowy w jego miejsce
  • rolling update — aktualizacja aplikacji przez stopniowe zastępowanie starych Podów nowymi, bez przestoju (downtime) całej usługi
  • load balancing — Service automatycznie rozdziela ruch między wszystkie zdrowe repliki danego Poda

Docker Compose vs Kubernetes

Docker ComposeKubernetes
Skalajedna maszynaklaster wielu maszyn
Złożonośćniska — jeden plik YAMLwysoka — wiele typów obiektów, własne API
Samonaprawa/autoscalingbrak natywniewbudowane
Typowe zastosowanielokalny development, małe wdrożeniaprodukcyjne środowiska o dużej skali/wymaganej odporności
Typowe pytanie: wyjaśnij, dlaczego Kubernetes jest bardziej odpowiedni niż Docker Compose dla aplikacji produkcyjnej o dużym, zmiennym obciążeniu — automatyczne skalowanie, samonaprawa i rozłożenie na wiele maszyn to funkcjonalności, których Compose (ograniczone do jednego hosta) nie zapewnia.
