Programowanie aplikacji internetowych (Java EE / Jakarta EE)

1. Elementy niezbędne do wdrożenia aplikacji Java EE/Jakarta

Kontener serwletów / serwer aplikacyjny

Aplikacja Java EE/Jakarta nie działa "samodzielnie" (jak prosty program z main()) — wymaga kontenera, który zarządza jej cyklem życia:

TypPrzykładyZakres
Kontener serwletówApache Tomcat, Jettyobsługuje serwlety, JSP — "lżejszy", bez pełnego zestawu usług EE
Pełny serwer aplikacyjnyWildFly, GlassFish, Payarapełne wsparcie specyfikacji Java EE/Jakarta (EJB, JMS, JTA, JPA i inne)

Archiwum WAR (Web Application Archive)

Standardowy format pakowania aplikacji webowej Java do wdrożenia — plik .war to skompresowane archiwum (jak ZIP) ze ustaloną strukturą katalogów:

moja-aplikacja.war
├── WEB-INF/
│   ├── web.xml           # deskryptor wdrożenia (opcjonalny od Servlet 3.0+)
│   ├── classes/          # skompilowane klasy .class
│   └── lib/              # zależne biblioteki .jar
├── index.jsp
└── inne zasoby statyczne (CSS, JS, obrazy)

WEB-INF jest niedostępny bezpośrednio z przeglądarki (bezpieczne miejsce na klasy/konfigurację) — pliki poza nim (jak index.jsp) są publicznie dostępne.

Deskryptor wdrożenia — web.xml

<web-app>
    <servlet>
        <servlet-name>MojServlet</servlet-name>
        <servlet-class>pl.przykład.MojServlet</servlet-class>
    </servlet>
    <servlet-mapping>
        <servlet-name>MojServlet</servlet-name>
        <url-pattern>/hello</url-pattern>
    </servlet-mapping>
</web-app>

Od Servlet 3.0 większość konfiguracji można zastąpić adnotacjami w kodzie (np. @WebServlet("/hello")) — web.xml stał się opcjonalny, choć wciąż używany np. do konfiguracji filtrów bezpieczeństwa czy stron błędów.

Proces wdrożenia (deployment)

  1. kompilacja kodu i spakowanie do archiwum .war (zwykle przez Maven/Gradle)
  2. skopiowanie/wgranie archiwum do katalogu wdrożeń serwera (np. webapps/ w Tomcacie) albo przez panel administracyjny serwera
  3. serwer automatycznie rozpakowuje i uruchamia aplikację, udostępniając ją pod danym kontekstem URL (np. /moja-aplikacja/)

Zależności — Maven/Gradle

Zarządzanie bibliotekami (np. sterownik JDBC, biblioteki JSON) zwykle przez Mavena (pom.xml) lub Gradle — automatyczne pobieranie i wersjonowanie zależności, analogicznie do package.json w Node.js czy requirements.txt w Pythonie.

Typowe pytanie: opisz pełną ścieżkę od napisanego kodu serwletu do działającej aplikacji dostępnej pod adresem URL — kompilacja, pakowanie do WAR, wdrożenie na serwer, konfiguracja mapowania URL.

2. Serwlet — budowa i zasada działania

Klasa Java rozszerzająca HttpServlet, obsługująca żądania HTTP po stronie serwera — podstawowy budulec aplikacji webowych w Java EE/Jakarta (analogicznie do kontrolera w MVC — patrz przedmiot Bazy danych w aplikacjach internetowych).

Podstawowa struktura serwletu

@WebServlet("/hello")
public class MojServlet extends HttpServlet {

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<h1>Witaj, świecie!</h1>");
    }

    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        String imie = request.getParameter("imie");
        response.getWriter().println("Cześć, " + imie);
    }
}

Cykl życia serwletu

  1. ładowanie i instancjonowanie — kontener tworzy jedną instancję serwletu (nie nową dla każdego żądania!) — zwykle przy pierwszym żądaniu albo przy starcie aplikacji
  2. init() — wywoływane raz, po utworzeniu instancji — inicjalizacja zasobów (np. połączenie z bazą)
  3. service() — wywoływane dla każdego żądania, deleguje do odpowiedniej metody (doGet, doPost itd.) w zależności od metody HTTP
  4. destroy() — wywoływane raz, przy usuwaniu serwletu/zamykaniu aplikacji — zwolnienie zasobów

Metody obsługi żądań HTTP

Metoda serwletuOdpowiadająca metoda HTTP
doGetGET — odczyt danych
doPostPOST — wysłanie danych (np. formularz)
doPutPUT — aktualizacja zasobu
doDeleteDELETE — usunięcie zasobu

Wielowątkowość serwletów

Kontener obsługuje wiele żądań do tej samej instancji serwletu w osobnych wątkach (jeden wątek na żądanie) — pola instancyjne serwletu są więc współdzielone między żądaniami i wymagają synchronizacji (patrz przedmiot Programowanie współbieżne), jeśli są modyfikowane! Dane specyficzne dla jednego żądania powinny być zmiennymi lokalnymi w metodzie doGet/doPost, nie polami klasy.

Filtry (Filters) i słuchacze (Listeners)

Filtr — pośredniczy w przetwarzaniu żądania przed/po serwletem (np. logowanie, uwierzytelnianie, kompresja) — może przetworzyć wiele różnych serwletów wg wzorca URL. Listener — reaguje na zdarzenia cyklu życia aplikacji/sesji (np. utworzenie sesji, uruchomienie aplikacji).

Typowe pytanie: prześledź cykl życia serwletu od pierwszego żądania klienta do zamknięcia aplikacji, i wyjaśnij, dlaczego pole instancyjne serwletu jest ryzykowne bez synchronizacji.

3. Sesje w Java EE/Jakarta

Dlaczego sesje są potrzebne

HTTP jest protokołem bezstanowym (patrz przedmiot Sieci komputerowe / Języki hipertekstowe) — serwer domyślnie nie "pamięta" nic między kolejnymi żądaniami tego samego klienta. Sesja pozwala powiązać serię żądań z jednym, konkretnym użytkownikiem/przeglądarką.

Tworzenie i obsługa sesji — HttpSession

protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    HttpSession sesja = request.getSession();    // tworzy nową sesję, jeśli nie istnieje

    Integer licznik = (Integer) sesja.getAttribute("licznik");
    if (licznik == null) licznik = 0;
    licznik++;
    sesja.setAttribute("licznik", licznik);

    response.getWriter().println("Odwiedziny: " + licznik);
}

request.getSession() — zwraca istniejącą sesję albo tworzy nową; request.getSession(false) — zwraca null, jeśli sesja nie istnieje (nie tworzy nowej).

Mechanizm identyfikacji sesji — Cookie JSESSIONID

Kontener automatycznie generuje unikalny identyfikator sesji i przesyła go do klienta jako cookie (JSESSIONID) — przy każdym kolejnym żądaniu przeglądarka odsyła to cookie, a serwer na tej podstawie odnajduje właściwy obiekt HttpSession po swojej stronie.

URL rewriting — alternatywa bez cookies

String url = response.encodeURL("strona.jsp");   // dopisuje identyfikator sesji do URL, jeśli cookies wyłączone

Awaryjny mechanizm, gdy klient ma wyłączone cookies — identyfikator sesji dopisywany bezpośrednio do adresu URL (mniej bezpieczny — widoczny w historii przeglądarki, logach serwera).

Atrybuty sesji

sesja.setAttribute("uzytkownik", obiektUzytkownika);
Object dane = sesja.getAttribute("uzytkownik");
sesja.removeAttribute("uzytkownik");
sesja.invalidate();    // zakończenie sesji (np. przy wylogowaniu)

Czas życia sesji

Sesja wygasa automatycznie po okresie braku aktywności (timeout, konfigurowalny w web.xml lub programowo: sesja.setMaxInactiveInterval(sekundy)) — nie jest to czas od utworzenia, a czas od ostatniego żądania powiązanego z tą sesją.

Przechowywanie stanu sesji na serwerze

Dane sesji (poza samym identyfikatorem) są przechowywane po stronie serwera (domyślnie w pamięci) — w odróżnieniu od cookies, gdzie same dane trzymane są u klienta. Przy wielu instancjach serwera (load balancing) wymaga to replikacji sesji albo mechanizmu "sticky session" (przypisania klienta zawsze do tego samego serwera).

Typowe pytanie: zaimplementuj prosty licznik odwiedzin lub mechanizm logowania z użyciem HttpSession, i wyjaśnij różnicę między sesją a cookie — cookie to mechanizm transportu identyfikatora, sesja to sam obiekt ze stanem po stronie serwera.

4. Baza danych: JDBC vs JPA

(podstawy JDBC — patrz przedmiot Programowanie sieciowe; tu porównanie z JPA w kontekście Java EE)

JDBC — niskopoziomowy dostęp do bazy

try (Connection conn = DriverManager.getConnection(url, user, pass);
     PreparedStatement stmt = conn.prepareStatement("SELECT * FROM Produkty WHERE id=?")) {
    stmt.setInt(1, 5);
    ResultSet rs = stmt.executeQuery();
    while (rs.next()) {
        System.out.println(rs.getString("nazwa"));
    }
}

Programista pisze ręcznie zapytania SQL i mapuje wyniki (ResultSet) na obiekty samodzielnie.

JPA — mapowanie obiektowo-relacyjne (ORM)

@Entity
@Table(name = "produkty")
public class Produkt {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String nazwa;
    private double cena;

    // gettery, settery
}

// użycie przez EntityManager
Produkt p = entityManager.find(Produkt.class, 5L);   // odpowiednik SELECT ... WHERE id=5
entityManager.persist(nowyProdukt);                   // odpowiednik INSERT
entityManager.remove(p);                               // odpowiednik DELETE

Programista operuje na obiektach (encjach), JPA "pod maską" generuje odpowiednie zapytania SQL — analogicznie do ORM w innych technologiach (patrz przedmiot Bazy danych w aplikacjach internetowych).

JPQL (Java Persistence Query Language)

List<Produkt> wynik = entityManager
    .createQuery("SELECT p FROM Produkt p WHERE p.cena > :min", Produkt.class)
    .setParameter("min", 100.0)
    .getResultList();

Zapytania w JPQL operują na encjach i ich polach (nie na tabelach/kolumnach SQL) — JPA tłumaczy je na konkretny dialekt SQL bazy docelowej, co daje przenośność między różnymi bazami danych.

Porównanie JDBC vs JPA

JDBCJPA
Poziom abstrakcjiniski — surowy SQL, ręczne mapowaniewysoki — obiekty (encje), automatyczne mapowanie
Ilość kodu "boilerplate"duża (Connection, Statement, ResultSet, zamykanie zasobów)mała (adnotacje na klasie, gotowe metody EntityManager)
Kontrola nad zapytaniempełna — dokładnie taki SQL, jaki napisanomniejsza — JPA generuje SQL, czasem nieoptymalny bez dodatkowego tuningu
Przenośność między bazamiograniczona (składnia SQL bywa specyficzna dla bazy)lepsza — JPQL/encje niezależne od konkretnej bazy
Krzywa uczenianiższa — "zwykły" SQLwyższa — trzeba zrozumieć mapowanie, cykl życia encji, cache
Wydajność dla złożonych/masowych operacjipotencjalnie lepsza (pełna kontrola)może wymagać dostrojenia (np. problem N+1 przy leniwym ładowaniu relacji)

Relacje między encjami (JPA)

@Entity
public class Zamowienie {
    @ManyToOne
    private Klient klient;

    @OneToMany(mappedBy = "zamowienie")
    private List<PozycjaZamowienia> pozycje;
}

Adnotacje @OneToMany, @ManyToOne, @ManyToMany odwzorowują relacje znane z modelowania ERD (patrz przedmiot Relacyjne bazy danych) bezpośrednio w kodzie Java.

Typowe pytanie: dla opisanego scenariusza (np. prosta operacja odczytu vs złożony raport z wielu tabel) uzasadnij wybór między JDBC a JPA — JPA dla typowych operacji CRUD na obiektach domenowych, JDBC gdy potrzebna pełna kontrola nad konkretnym, zoptymalizowanym zapytaniem.

5. JSP i JSF — frameworki widoku

JSP (JavaServer Pages)

Technologia pozwalająca mieszać statyczny HTML z kodem Java osadzonym wewnątrz strony — plik .jsp jest przy pierwszym żądaniu kompilowany przez kontener do zwykłego serwletu.

<html>
<body>
    <h1>Lista produktów</h1>
    <ul>
    <% for (Produkt p : produkty) { %>
        <li><%= p.getNazwa() %> - <%= p.getCena() %> zł</li>
    <% } %>
    </ul>
</body>
</html>

Elementy składni JSP

ElementZastosowanie
<% kod java %>scriptlet — dowolny kod Java
<%= wyrażenie %>wypisanie wartości wyrażenia do HTML
<%@ page ... %>dyrektywa strony (import, kodowanie znaków)
JSTL (<c:forEach>, <c:if>)biblioteka tagów — zalecana alternatywa dla scriptletów, czytelniejsza, bliższa "czystemu" HTML
EL (Expression Language, ${...})uproszczony dostęp do atrybutów (żądania, sesji, aplikacji) bez pisania jawnego kodu Java
Dobra praktyka (i zgodnie z MVC, patrz przedmiot Bazy danych w aplikacjach internetowych): JSP powinien zawierać głównie prezentację (widok), a logika biznesowa i dostęp do danych powinny być w serwletach/klasach modelu — nadmiar scriptletów w JSP to "code smell" łamiący separację odpowiedzialności.

JSF (JavaServer Faces)

Framework wyższego poziomu niż JSP — komponentowy model UI (podobny do desktopowych frameworków GUI), z automatycznym zarządzaniem stanem i cyklem żądania.

<h:form>
    <h:inputText value="#{produktBean.nazwa}" />
    <h:commandButton value="Zapisz" action="#{produktBean.zapisz}" />
</h:form>

Managed Beans

Klasy Java powiązane z widokiem JSF (przez @ManagedBean/@Named lub CDI @Inject) — komponenty JSF (jak <h:inputText>) automatycznie odczytują/zapisują wartości pól tych klas, bez ręcznego parsowania parametrów żądania (jak trzeba by robić w "gołym" serwlecie).

Cykl życia żądania JSF (6 faz)

  1. Odtworzenie drzewa komponentów (Restore View)
  2. Zastosowanie wartości żądania (Apply Request Values)
  3. Walidacja (Process Validations)
  4. Aktualizacja modelu (Update Model Values)
  5. Wywołanie logiki aplikacji (Invoke Application)
  6. Wygenerowanie odpowiedzi (Render Response)

Znacznie bardziej złożony i "zarządzany" niż prosty cykl serwletu (żądanie → odpowiedź) — JSF automatyzuje konwersję typów, walidację i synchronizację stanu komponentów z modelem.

Porównanie JSP vs JSF

JSPJSF
Model programowaniaskrypt generujący HTML (podobny do PHP)komponentowy, zdarzeniowy (podobny do aplikacji desktopowych)
Zarządzanie stanemręczne (przez sesję/żądanie)automatyczne (drzewo komponentów, Managed Beans)
Złożonośćniższa, bliższa "czystemu" HTML+Javawyższa, więcej "magii" frameworka
Kontrola nad wygenerowanym HTMLpełnaograniczona (komponenty renderują swój własny HTML)
Typowe pytanie: napisz prosty formularz w JSP (ze scriptletem/JSTL) i jego odpowiednik w JSF (z Managed Bean), porównując ilość i charakter kodu potrzebnego w obu podejściach.

6. JAX-RS — RESTful Web Services w Java EE

Natywna specyfikacja Java EE/Jakarta do budowania REST API — alternatywa dla "gołych" serwletów (punkt 2), znacznie lepiej dopasowana do zwracania danych (JSON/XML) niż generowania HTML.

Podstawowy zasób REST

@Path("/produkty")
public class ProduktResource {

    @GET
    @Produces(MediaType.APPLICATION_JSON)
    public List<Produkt> wszystkie() {
        return produktService.znajdzWszystkie();
    }

    @GET
    @Path("/{id}")
    @Produces(MediaType.APPLICATION_JSON)
    public Produkt jeden(@PathParam("id") Long id) {
        return produktService.znajdzPoId(id);
    }

    @POST
    @Consumes(MediaType.APPLICATION_JSON)
    public Response dodaj(Produkt p) {
        produktService.zapisz(p);
        return Response.status(Response.Status.CREATED).entity(p).build();
    }

    @PUT
    @Path("/{id}")
    @Consumes(MediaType.APPLICATION_JSON)
    public Produkt aktualizuj(@PathParam("id") Long id, Produkt p) { ... }

    @DELETE
    @Path("/{id}")
    public Response usun(@PathParam("id") Long id) {
        produktService.usun(id);
        return Response.noContent().build();
    }
}

Kluczowe adnotacje

AdnotacjaZnaczenie
@Pathścieżka URL zasobu/metody (może zawierać parametry {id})
@GET/@POST/@PUT/@DELETEmetoda HTTP obsługiwana przez daną metodę Java
@Producestyp MIME zwracanej odpowiedzi (np. JSON, XML)
@Consumestyp MIME oczekiwanego ciała żądania
@PathParamwartość wyciągnięta z segmentu ścieżki URL
@QueryParamwartość z parametru zapytania (?klucz=wartosc)

Automatyczna konwersja JSON — JAX-B/JSON-B

JAX-RS automatycznie (przy odpowiedniej konfiguracji dostawcy, np. Jackson lub JSON-B) zamienia obiekty Java na JSON i odwrotnie — programista operuje na zwykłych obiektach (podobnie jak encje JPA, patrz punkt 4), bez ręcznego budowania stringów JSON.

JAX-RS vs zwykły serwlet

SerwletJAX-RS
Naturalne zastosowaniegenerowanie HTML, obsługa formularzyAPI zwracające dane (JSON/XML)
Mapowanie URL/metod HTTPręczne (doGet/doPost, jeden URL pattern na serwlet)deklaratywne przez adnotacje, wiele metod/ścieżek w jednej klasie zasobu
Parsowanie danychręczne (request.getParameter)automatyczne wstrzykiwanie parametrów/ciała żądania
Powiązanie z innymi przedmiotami: JAX-RS to odpowiednik tego, co Spring Boot (@RestController) robi w ekosystemie Spring (patrz przedmiot Programowanie sieciowe) — inna biblioteka/specyfikacja, ta sama idea REST API z CRUD.

7. Bezpieczeństwo w Java EE/Jakarta

Uwierzytelnianie zarządzane przez kontener

Java EE pozwala delegować logikę logowania do kontenera (serwera aplikacyjnego), zamiast implementować ją ręcznie w kodzie — konfiguracja w web.xml:

<login-config>
    <auth-method>FORM</auth-method>
    <form-login-config>
        <form-login-page>/logowanie.jsp</form-login-page>
        <form-error-page>/blad-logowania.jsp</form-error-page>
    </form-login-config>
</login-config>

Metody uwierzytelniania (auth-method)

MetodaZasada
BASICwbudowane okno logowania przeglądarki (login/hasło w nagłówku HTTP, kodowane Base64 — nie szyfrowane, wymaga HTTPS)
FORMwłasny, konfigurowalny formularz logowania (HTML/JSP) — najczęściej używane w praktyce
CLIENT-CERTuwierzytelnianie certyfikatem klienckim (TLS mutual auth)

Autoryzacja — role i ograniczenia dostępu

<security-constraint>
    <web-resource-collection>
        <url-pattern>/admin/*</url-pattern>
    </web-resource-collection>
    <auth-constraint>
        <role-name>ADMIN</role-name>
    </auth-constraint>
</security-constraint>

Deklaratywne ograniczenie — wszystkie zasoby pod /admin/* wymagają roli ADMIN, weryfikowanej automatycznie przez kontener przed dotarciem żądania do serwletu — programista nie musi pisać tej logiki ręcznie.

Adnotacje bezpieczeństwa (programowe, na poziomie klas/metod)

@RolesAllowed("ADMIN")
public class AdminServlet extends HttpServlet { ... }

@GET
@RolesAllowed({"ADMIN", "MODERATOR"})
public List<Uzytkownik> wszyscyUzytkownicy() { ... }   // np. w zasobie JAX-RS z punktu 6
AdnotacjaZnaczenie
@RolesAlloweddostęp tylko dla wskazanych ról
@PermitAlldostęp dla każdego (uwierzytelnionego lub nie)
@DenyAllzablokowanie dostępu dla wszystkich

Sprawdzanie roli/tożsamości programowo

protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    if (request.isUserInRole("ADMIN")) {
        // logika dostępna tylko dla administratora
    }
    Principal uzytkownik = request.getUserPrincipal();   // tożsamość zalogowanego użytkownika (lub null)
}

Bezpieczeństwo deklaratywne vs programowe

Deklaratywne (web.xml, adnotacje)Programowe (kod w serwlecie)
Gdzie logikakonfiguracja, poza kodem biznesowymwewnątrz metod, jawnie sprawdzane
Elastycznośćniższa — proste reguły "ścieżka → rola"wyższa — dowolnie złożone warunki
Łatwość utrzymaniałatwiej przeglądać reguły w jednym miejscurozproszone po kodzie
Zasada ogólna: preferuj bezpieczeństwo deklaratywne, gdy reguły są proste (rola → dostęp do ścieżki) — kontener robi to automatycznie, przed jakimkolwiek kodem aplikacji; sięgaj po sprawdzanie programowe, gdy potrzebna bardziej złożona logika (np. "użytkownik może edytować tylko własne zamówienia").
