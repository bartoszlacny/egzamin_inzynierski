Programowanie sieciowe (Java)

1. Programowanie wielowątkowe w Javie

Tworzenie wątków

// przez dziedziczenie po Thread
class MojWatek extends Thread {
    public void run() {
        System.out.println("Działam w wątku!");
    }
}
new MojWatek().start();

// przez implementację Runnable (preferowane — nie "blokuje" jedynego dziedziczenia)
Runnable zadanie = () -> System.out.println("Działam w wątku!");
new Thread(zadanie).start();
Wywołanie run() bezpośrednio (bez start()) wykonuje kod w tym samym, aktualnym wątku — nie tworzy nowego! Klasyczna pułapka egzaminacyjna.

Synchronizacja — synchronized

class Licznik {
    private int wartosc = 0;
    public synchronized void zwieksz() {   // tylko jeden wątek naraz może wykonać tę metodę
        wartosc++;
    }
}

Zapobiega race condition (wyścigowi) przy dostępie wielu wątków do współdzielonego stanu — analogicznie do mutexów/semaforów (patrz przedmiot Wprowadzenie do systemów operacyjnych).

Executor Framework (nowocześniejsze podejście)

ExecutorService pool = Executors.newFixedThreadPool(4);   // pula 4 wątków

for (int i = 0; i < 10; i++) {
    int zadanieId = i;
    pool.submit(() -> System.out.println("Zadanie " + zadanieId));
}
pool.shutdown();

Zarządzanie pulą wątków przez ExecutorService jest wydajniejsze i bezpieczniejsze niż ręczne tworzenie new Thread() dla każdego zadania — unika narzutu tworzenia/niszczenia wątków przy dużej liczbie krótkich zadań.

Future i CompletableFuture — wynik asynchroniczny

CompletableFuture<Integer> wynik = CompletableFuture.supplyAsync(() -> {
    // długo trwające obliczenie
    return 42;
});

wynik.thenAccept(v -> System.out.println("Wynik: " + v));

Klasyczne problemy współbieżności

Race condition, deadlock (patrz przedmiot Wprowadzenie do systemów operacyjnych — te same koncepcje, teraz w kontekście wątków Javy), starvation (zagłodzenie — wątek nigdy nie dostaje szansy na wykonanie).

Wielowątkowość jest kluczowa w programowaniu sieciowym — serwer obsługujący wielu klientów jednocześnie (patrz punkt 3) typowo przydziela osobny wątek (lub zadanie w puli wątków) na każde połączenie klienta, żeby jeden wolny/zawieszony klient nie blokował obsługi innych.

2. Połączenie z bazą danych (JDBC)

JDBC (Java Database Connectivity) — podstawy

String url = "jdbc:mysql://localhost:3306/mojabaza";
Connection conn = DriverManager.getConnection(url, "user", "haslo");

Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery("SELECT id, nazwa FROM Produkty");

while (rs.next()) {
    System.out.println(rs.getInt("id") + ": " + rs.getString("nazwa"));
}

conn.close();

PreparedStatement — zapytania przygotowane (bezpieczne!)

String sql = "SELECT * FROM Uzytkownicy WHERE login = ? AND haslo = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, login);
pstmt.setString(2, hashHasla);
ResultSet rs = pstmt.executeQuery();
Jak w każdym innym języku (patrz przedmioty Języki hipertekstowe, Relacyjne bazy danych) — PreparedStatement chroni przed SQL injection; nigdy nie wklejać danych użytkownika bezpośrednio do stringa zapytania.

Try-with-resources — automatyczne zamykanie połączeń

try (Connection conn = DriverManager.getConnection(url, user, pass);
     PreparedStatement pstmt = conn.prepareStatement(sql)) {
    // ...
} catch (SQLException e) {
    e.printStackTrace();
}
// conn i pstmt automatycznie zamknięte, nawet przy wyjątku

Connection pooling

Tworzenie nowego połączenia z bazą jest kosztowne (czasowo) — w aplikacjach sieciowych obsługujących wielu klientów jednocześnie używa się puli połączeń (np. HikariCP) — połączenia są tworzone raz i wielokrotnie "wypożyczane"/"oddawane", zamiast tworzone od zera dla każdego żądania.

Transakcje w JDBC

conn.setAutoCommit(false);
try {
    // kilka operacji...
    conn.commit();
} catch (SQLException e) {
    conn.rollback();
}

(pełne omówienie transakcji i ACID — patrz przedmiot Relacyjne bazy danych)

ORM w Javie (dla kontekstu)

Hibernate/JPA — mapowanie obiektowo-relacyjne analogiczne do ORM w innych językach (patrz przedmiot Bazy danych w aplikacjach internetowych) — pozwala operować na obiektach Java, bez pisania SQL "ręcznie" dla każdej operacji.

3. Aplikacje klient-serwer (TCP/UDP)

Gniazda (sockets) — podstawy

Java udostępnia klasy Socket (klient) i ServerSocket (serwer) dla TCP, oraz DatagramSocket dla UDP.

Serwer TCP

ServerSocket serwer = new ServerSocket(8080);
while (true) {
    Socket klient = serwer.accept();          // blokuje, aż połączy się klient
    new Thread(() -> obsluzKlienta(klient)).start();  // osobny wątek na klienta (patrz punkt 1)
}

void obsluzKlienta(Socket klient) {
    try (BufferedReader in = new BufferedReader(new InputStreamReader(klient.getInputStream()));
         PrintWriter out = new PrintWriter(klient.getOutputStream(), true)) {
        String linia = in.readLine();
        out.println("Echo: " + linia);
    } catch (IOException e) { e.printStackTrace(); }
}

Klient TCP

Socket socket = new Socket("localhost", 8080);
PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
BufferedReader in = new BufferedReader(new InputStreamReader(socket.getInputStream()));

out.println("Witaj serwerze!");
String odpowiedz = in.readLine();
System.out.println(odpowiedz);

UDP — bez połączenia

// serwer UDP
DatagramSocket serwerSocket = new DatagramSocket(9090);
byte[] bufor = new byte[1024];
DatagramPacket pakiet = new DatagramPacket(bufor, bufor.length);
serwerSocket.receive(pakiet);   // odbierz jeden pakiet

// klient UDP
DatagramSocket clientSocket = new DatagramSocket();
byte[] dane = "Witaj".getBytes();
DatagramPacket wyslany = new DatagramPacket(dane, dane.length, InetAddress.getByName("localhost"), 9090);
clientSocket.send(wyslany);

Obsługa wielu klientów jednocześnie

Serwer w pętli accept() obsługuje kolejnych klientów — dla współbieżnej obsługi wielu klientów naraz każde połączenie zwykle delegowane do osobnego wątku lub zadania w puli wątków (ExecutorService, patrz punkt 1) — inaczej serwer obsłużyłby tylko jednego klienta na raz.

Typowe zadanie projektowe: prosty serwer echo/czat TCP obsługujący wielu klientów jednocześnie, każdy w osobnym wątku, plus prosty protokół tekstowy (np. linia = jedna komenda).

4. Operacje na plikach w Javie

Podstawowe API — java.io

try (BufferedReader reader = new BufferedReader(new FileReader("dane.txt"))) {
    String linia;
    while ((linia = reader.readLine()) != null) {
        System.out.println(linia);
    }
}

try (BufferedWriter writer = new BufferedWriter(new FileWriter("wynik.txt"))) {
    writer.write("Nowa linia");
    writer.newLine();
}

Nowsze API — java.nio.file (Path, Files)

Path plik = Path.of("dane.txt");

List<String> linie = Files.readAllLines(plik);        // wczytanie całego pliku od razu
Files.writeString(plik, "nowa treść");                  // proste zapisanie
Files.exists(plik);
Files.copy(plik, Path.of("kopia.txt"));
Files.delete(plik);

try (Stream<String> stream = Files.lines(plik)) {       // strumieniowe (efektywne pamięciowo) przetwarzanie
    stream.filter(l -> l.contains("błąd")).forEach(System.out::println);
}

Operacje binarne

byte[] dane = Files.readAllBytes(Path.of("obraz.png"));
Files.write(Path.of("kopia.png"), dane);

Serializacja obiektów

// zapis obiektu do pliku
try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("obiekt.dat"))) {
    out.writeObject(mojObiekt);   // klasa musi implementować Serializable
}

// odczyt
try (ObjectInputStream in = new ObjectInputStream(new FileInputStream("obiekt.dat"))) {
    MojaKlasa obiekt = (MojaKlasa) in.readObject();
}

Zastosowanie w kontekście sieciowym

Operacje na plikach są istotne w programowaniu sieciowym przy: logowaniu zdarzeń serwera do plików, wczytywaniu konfiguracji (adresy, porty, dane logowania do bazy), zapisie/odczycie danych przesyłanych przez protokoły plikowe (np. FTP — patrz punkt 5).

W nowym kodzie zaleca się java.nio.file (Path/Files) nad starszym java.io.File — czytelniejsze API, lepsza obsługa błędów, wsparcie dla strumieniowego przetwarzania dużych plików.

REST API z CRUD (do projektu na ocenę 4.0)

W Javie zwykle realizowane przez framework Spring Boot — mapowanie metod HTTP na operacje CRUD (Create, Read, Update, Delete):

@RestController
@RequestMapping("/produkty")
public class ProduktController {

    @GetMapping                       // READ (wszystkie)
    public List<Produkt> wszystkie() { ... }

    @GetMapping("/{id}")               // READ (jeden)
    public Produkt jeden(@PathVariable Long id) { ... }

    @PostMapping                       // CREATE
    public Produkt dodaj(@RequestBody Produkt p) { ... }

    @PutMapping("/{id}")               // UPDATE
    public Produkt aktualizuj(@PathVariable Long id, @RequestBody Produkt p) { ... }

    @DeleteMapping("/{id}")            // DELETE
    public void usun(@PathVariable Long id) { ... }
}

Połączenie z bazą danych (punkt 2) zwykle realizowane przez Spring Data JPA (ORM), integracja z zewnętrznym API — przez RestTemplate/WebClient wołające inne serwisy REST.

Mikrousługi (do projektu na ocenę 5.0)

Architektura, w której aplikacja jest podzielona na kilka niezależnych serwisów (patrz przedmiot Projektowanie aplikacji internetowych), komunikujących się przez sieć — każdy serwis może być rozwijany, wdrażany i skalowany niezależnie.

Komunikacja asynchroniczna — RabbitMQ

Broker komunikatów — serwisy nie komunikują się bezpośrednio (jak w REST, gdzie klient czeka na odpowiedź), a wysyłają wiadomości do kolejki; inny serwis odbiera je, kiedy jest gotowy — nadawca nie musi czekać na przetworzenie.

// producent (Java, biblioteka amqp-client)
ConnectionFactory factory = new ConnectionFactory();
factory.setHost("localhost");
try (Connection conn = factory.newConnection(); Channel channel = conn.createChannel()) {
    channel.queueDeclare("zamowienia", false, false, false, null);
    channel.basicPublish("", "zamowienia", null, "Nowe zamówienie #123".getBytes());
}

Zalety: odsprzęglenie (decoupling) serwisów — nadawca nie musi znać/czekać na odbiorcę; naturalna odporność na chwilowe przeciążenie/awarię odbiorcy (wiadomości czekają w kolejce).

MQTT — protokół dla IoT/lekkiej komunikacji

Lekki protokół publish-subscribe, zaprojektowany dla urządzeń o ograniczonych zasobach (IoT) i niestabilnych połączeniach sieciowych — mniejszy narzut niż RabbitMQ/AMQP, popularny w systemach czujników/urządzeń wbudowanych.

RabbitMQ (AMQP)MQTT
Typowe zastosowaniekomunikacja między mikroserwisami backendukomunikacja z urządzeniami IoT, telemetria
Narzut protokołuwiększy, bardziej "rozgadany"bardzo mały — zoptymalizowany pod słabe sieci/urządzenia
Modelkolejki, routing (exchanges)publish/subscribe na "topicach"

Wzorzec publish-subscribe (pub/sub)

Nadawca (publisher) wysyła wiadomość do tematu (topic), nie do konkretnego odbiorcy — wszyscy zainteresowani odbiorcy (subscribers), którzy "zapisali się" na ten temat, otrzymują wiadomość — pełne odsprzęglenie liczby i identyfikacji odbiorców od nadawcy.

Typowe pytanie projektowe: zaprojektuj architekturę 2-3 mikroserwisów (np. serwis zamówień, serwis powiadomień, serwis magazynu) komunikujących się asynchronicznie przez RabbitMQ — serwis zamówień publikuje zdarzenie "nowe zamówienie", serwisy powiadomień i magazynu subskrybują je niezależnie, bez wzajemnej bezpośredniej zależności.
