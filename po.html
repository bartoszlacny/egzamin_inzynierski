Programowanie obiektowe (C++)

1. Klasa i obiekt

Klasa to szablon (definicja) opisujący dane (pola/atrybuty) i zachowanie (metody) — obiekt to konkretna instancja tej klasy, istniejąca w pamięci.

class Osoba {
public:
    std::string imie;
    int wiek;

    void przywitaj() {
        std::cout << "Czesc, jestem " << imie << std::endl;
    }
};

int main() {
    Osoba o1;              // obiekt (instancja klasy Osoba)
    o1.imie = "Jan";
    o1.wiek = 25;
    o1.przywitaj();

    Osoba o2;               // inny, niezależny obiekt tej samej klasy
    o2.imie = "Anna";
}

Pola i metody

  • pola (atrybuty) — dane przechowywane przez obiekt, każdy obiekt ma własną kopię
  • metody — funkcje należące do klasy, operujące na danych obiektu (mają domyślny dostęp do jego pól)

Wskaźnik this

W każdej metodzie niestatycznej dostępny jest wskaźnik this, wskazujący na obiekt, na którym metoda została wywołana — przydatny np. gdy nazwa parametru jest taka sama jak nazwa pola:

void ustawWiek(int wiek) {
    this->wiek = wiek;   // this->wiek to pole, wiek (bez this) to parametr
}
Różnica klasa vs obiekt to jak przepis (klasa) i konkretnie upieczony tort (obiekt) — z jednego przepisu można "wypiec" wiele niezależnych tortów (obiektów), każdy ze swoimi wartościami pól.

2. Dziedziczenie, polimorfizm, enkapsulacja

Dziedziczenie

Klasa (pochodna/derived) może przejąć pola i metody innej klasy (bazowej/base), rozszerzając lub nadpisując jej zachowanie — realizuje relację "jest rodzajem" (is-a).

class Zwierze {
public:
    std::string imie;
    void jedz() { std::cout << imie << " jadlo\n"; }
    virtual void wydajDzwiek() { std::cout << "..." << std::endl; }
};

class Pies : public Zwierze {
public:
    void wydajDzwiek() override { std::cout << "Hau!" << std::endl; }
};

Polimorfizm

Możliwość traktowania obiektów różnych klas pochodnych jednolicie (przez wskaźnik/referencję do klasy bazowej), przy czym wywołana zostaje właściwa (nadpisana) wersja metody dla konkretnego obiektu:

Zwierze *z = new Pies();
z->wydajDzwiek();   // wypisze "Hau!", nie "..." — dzięki polimorfizmowi

Wymaga słowa virtual przy metodzie w klasie bazowej — bez tego wywołanie "przywiązałoby się" statycznie do wersji z klasy bazowej (tzw. early binding), a nie do rzeczywistego typu obiektu (late binding / dynamic dispatch).

Enkapsulacja (hermetyzacja)

Ukrywanie wewnętrznej implementacji/danych klasy i udostępnianie tylko kontrolowanego interfejsu (metod publicznych) — pola prywatne (private) są dostępne tylko przez metody klasy (np. gettery/settery), co chroni przed niekontrolowaną, niepoprawną zmianą stanu obiektu z zewnątrz.

class KontoBankowe {
private:
    double saldo;
public:
    void wplac(double kwota) {
        if (kwota > 0) saldo += kwota;   // kontrola poprawności
    }
    double getSaldo() { return saldo; }
};
Enkapsulacja, dziedziczenie i polimorfizm to trzy fundamentalne "filary" programowania obiektowego (razem z abstrakcją) — pytania o ich definicje i wzajemne relacje są bardzo częste na egzaminach.

3. Klasy abstrakcyjne

Klasa, której nie można utworzyć instancji — służy jako "szablon" dla klas pochodnych, definiując interfejs, który muszą zaimplementować.

Metoda czysto wirtualna (pure virtual)

class Figura {
public:
    virtual double pole() = 0;   // "= 0" — metoda czysto wirtualna, brak implementacji
};

class Kwadrat : public Figura {
    double bok;
public:
    Kwadrat(double b) : bok(b) {}
    double pole() override { return bok * bok; }  // musi zaimplementować
};

// Figura f;         // BŁĄD KOMPILACJI — nie można stworzyć obiektu klasy abstrakcyjnej
Kwadrat k(5);        // OK, klasa pochodna implementuje metodę
Figura *f = &k;       // OK — wskaźnik/referencja do klasy abstrakcyjnej jest dozwolona

Zasada

Klasa jest abstrakcyjna, jeśli ma przynajmniej jedną metodę czysto wirtualną. Klasa pochodna musi zaimplementować wszystkie metody czysto wirtualne, żeby móc utworzyć jej instancje — w innym wypadku sama również pozostaje abstrakcyjna.

Interfejs

Klasa abstrakcyjna, w której wszystkie metody są czysto wirtualne (brak żadnej implementacji, brak pól z danymi) — czysty "kontrakt" określający, jakie metody musi mieć klasa implementująca, bez żadnej wspólnej logiki.

Zastosowanie: klasy abstrakcyjne wymuszają wspólny interfejs dla rodziny podobnych klas (np. różne rodzaje figur, wszystkie muszące mieć metodę pole()), umożliwiając polimorficzne operowanie na nich przez wskaźnik/referencję do klasy bazowej.

4. Wskaźniki, referencje, dynamiczna pamięć w C++

Wskaźniki (jak w C)

int x = 5;
int *p = &x;
*p = 10;   // x = 10

Referencje — "alias" na istniejącą zmienną

int x = 5;
int &r = x;   // r to alias dla x, NIE nowa zmienna
r = 10;       // x = 10 też!
// referencja musi być zainicjalizowana przy deklaracji i nie może zostać "przestawiona" na inny obiekt
WskaźnikReferencja
może być NULL/nullptrtaknie (musi wskazywać na istniejący obiekt)
można zmienić celtak (przestawić na inny adres)nie (raz ustalona, zawsze ten sam obiekt)
składnia dostępuprzez *, ->bezpośrednio, jak zwykła zmienna
typowe użyciedynamiczna alokacja, struktury danychparametry funkcji (unikanie kopiowania)

Przekazywanie parametrów przez referencję

void zwieksz(int &x) { x++; }   // modyfikuje oryginał, bez narzutu wskaźnika w kodzie
void wypisz(const std::string &s) { std::cout << s; }  // unika kopiowania dużego obiektu

Dynamiczna alokacja w C++: new / delete

int *p = new int(5);         // alokacja pojedynczej wartości
int *tab = new int[10];      // alokacja tablicy

delete p;                    // zwolnienie pojedynczej wartości
delete[] tab;                // zwolnienie tablicy — inny operator!

Osoba *o = new Osoba();      // wywołuje też konstruktor
delete o;                    // wywołuje destruktor, potem zwalnia pamięć
new/delete (C++) różnią się od malloc/free (C) tym, że automatycznie wywołują konstruktor/destruktor obiektu — malloc tylko rezerwuje pamięć, nie inicjalizuje obiektu w sensie C++.

Smart pointery (nowoczesny C++)

std::unique_ptr, std::shared_ptr — automatycznie zarządzają czasem życia obiektu i wywołują delete w odpowiednim momencie, znacznie redukując ryzyko wycieków pamięci względem ręcznego new/delete.

5. Przeciążanie operatorów, funkcji, funkcje zaprzyjaźnione

Przeciążanie funkcji (function overloading)

Kilka funkcji o tej samej nazwie, różniących się listą parametrów (liczbą lub typami) — kompilator wybiera odpowiednią wersję na podstawie argumentów wywołania:

int dodaj(int a, int b) { return a+b; }
double dodaj(double a, double b) { return a+b; }
int dodaj(int a, int b, int c) { return a+b+c; }

Przeciążanie operatorów (operator overloading)

Definiowanie własnego znaczenia operatorów (+, ==, << itd.) dla własnych klas:

class Wektor2D {
public:
    double x, y;
    Wektor2D operator+(const Wektor2D &inny) const {
        return Wektor2D{x+inny.x, y+inny.y};
    }
    bool operator==(const Wektor2D &inny) const {
        return x==inny.x && y==inny.y;
    }
};

Wektor2D a{1,2}, b{3,4};
Wektor2D c = a + b;   // wywołuje operator+ → c = {4,6}

Funkcje zaprzyjaźnione (friend)

Funkcja (lub inna klasa) zadeklarowana jako friend ma dostęp do prywatnych i chronionych składników klasy, mimo że sama nie jest jej metodą — łamie zasadę pełnej enkapsulacji w kontrolowany, jawnie zadeklarowany sposób.

class Wektor2D {
private:
    double x, y;
public:
    Wektor2D(double x, double y) : x(x), y(y) {}
    friend void wypisz(const Wektor2D &w);   // zaprzyjaźniona funkcja
};

void wypisz(const Wektor2D &w) {
    std::cout << w.x << ", " << w.y;   // dostęp do prywatnych x, y!
}
Typowe zastosowanie friend: przeciążenie operatora << do wypisywania obiektu na std::cout — musi być funkcją niebędącą metodą klasy (bo lewy argument to ostream, nie obiekt klasy), a jednocześnie potrzebuje dostępu do prywatnych pól.

6. Poziomy dostępu i składniki statyczne

Poziomy dostępu

ModyfikatorDostęp
publicdostępny z każdego miejsca w programie
protecteddostępny w danej klasie i klasach z niej dziedziczących, ale nie "z zewnątrz"
privatedostępny tylko w danej klasie (nie nawet w klasach dziedziczących)

W C++ domyślny dostęp w class to private, w struct to public.

Dziedziczenie i poziomy dostępu

class Bazowa {
protected:
    int chronione;
private:
    int prywatne;
};

class Pochodna : public Bazowa {
    void metoda() {
        chronione = 5;   // OK — protected dostępne w klasie pochodnej
        // prywatne = 5;  // BŁĄD — private niedostępne nawet w klasie pochodnej
    }
};

Pola statyczne (static)

Pole współdzielone przez wszystkie obiekty danej klasy — istnieje jedna kopia, niezależnie od liczby stworzonych obiektów:

class Licznik {
public:
    static int liczbaObiektow;   // deklaracja
    Licznik() { liczbaObiektow++; }
};
int Licznik::liczbaObiektow = 0;  // definicja i inicjalizacja poza klasą (wymagane!)

Licznik a, b, c;
std::cout << Licznik::liczbaObiektow;   // 3 — dostęp przez nazwę klasy, nie obiekt

Metody statyczne

Metoda należąca do klasy, nie do konkretnego obiektu — nie ma dostępu do this ani do pól niestatycznych (bo nie jest związana z żadnym konkretnym obiektem):

class Matematyka {
public:
    static int kwadrat(int x) { return x*x; }
};

int wynik = Matematyka::kwadrat(5);   // wywołanie bez tworzenia obiektu

7. Konstruktory i destruktory

Konstruktor

Specjalna metoda wywoływana automatycznie przy tworzeniu obiektu — inicjalizuje jego stan. Ma tę samą nazwę co klasa, brak typu zwracanego.

class Punkt {
public:
    double x, y;
    Punkt() : x(0), y(0) {}                  // konstruktor domyślny
    Punkt(double x, double y) : x(x), y(y) {} // konstruktor parametryczny
    Punkt(const Punkt &inny) : x(inny.x), y(inny.y) {} // konstruktor kopiujący
};

Punkt p1;              // wywołuje konstruktor domyślny
Punkt p2(1.0, 2.0);    // wywołuje konstruktor parametryczny
Punkt p3 = p2;         // wywołuje konstruktor kopiujący

Lista inicjalizacyjna

: x(x), y(y) — inicjalizuje pola przed wejściem do ciała konstruktora; wymagana np. dla pól const, referencji, i pól klas bez konstruktora domyślnego.

Konstruktor kopiujący

Wywoływany, gdy nowy obiekt jest tworzony jako kopia istniejącego — domyślny (generowany przez kompilator) kopiuje pola "płasko" (shallow copy); jeśli klasa zarządza zasobami (np. pamięcią przez wskaźnik), trzeba go zdefiniować samodzielnie (deep copy), żeby uniknąć współdzielenia tego samego zasobu przez dwa obiekty.

Destruktor

Wywoływany automatycznie przy usuwaniu obiektu (koniec zasięgu dla obiektu na stosie, albo jawne delete dla obiektu na stercie) — zwalnia zasoby przydzielone przez obiekt:

class Bufor {
    int *dane;
public:
    Bufor(int n) { dane = new int[n]; }
    ~Bufor() { delete[] dane; }   // destruktor — zwalnia pamięć
};

{
    Bufor b(10);
}  // koniec bloku → automatyczne wywołanie ~Bufor()
Destruktor klasy bazowej powinien być virtual, jeśli klasa ma być używana polimorficznie (przez wskaźnik do klasy bazowej) — inaczej delete na wskaźniku bazowym wywoła tylko destruktor bazowy, pomijając destruktor klasy pochodnej (wyciek pamięci/zasobów pochodnej klasy).

8. Obsługa wyjątków i biblioteka STL

Wyjątki — try / catch / throw

double dziel(double a, double b) {
    if (b == 0) {
        throw std::runtime_error("Dzielenie przez zero!");
    }
    return a / b;
}

int main() {
    try {
        double wynik = dziel(10, 0);
    } catch (const std::runtime_error &e) {
        std::cout << "Blad: " << e.what() << std::endl;
    } catch (...) {
        std::cout << "Nieznany blad" << std::endl;   // wyłapuje wszystko inne
    }
}
  • throw — zgłasza wyjątek (obiekt jakiegoś typu, często dziedziczący po std::exception)
  • try — blok kodu, w którym monitorowane są wyjątki
  • catch — obsługa konkretnego typu wyjątku; można mieć wiele bloków catch dla różnych typów
  • gdy wyjątek nie zostanie obsłużony, program się zatrzymuje (przez std::terminate)

Hierarchia std::exception

Standardowe klasy wyjątków (std::runtime_error, std::logic_error, std::out_of_range itd.) dziedziczą po std::exception — można wyłapać wiele typów jedną klauzulą catch(const std::exception &e), korzystając z polimorfizmu.

Biblioteka STL (Standard Template Library)

Zbiór gotowych, ogólnych (generycznych, szablonowych) kontenerów, algorytmów i iteratorów.

Podstawowe kontenery STL

KontenerCharakterystyka
std::vectordynamiczna tablica — szybki dostęp po indeksie, wolniejsze wstawianie w środku
std::listlista dwukierunkowa — szybkie wstawianie/usuwanie, wolny dostęp po indeksie
std::maptablica asocjacyjna (klucz→wartość), zwykle jako drzewo zbalansowane, \(O(\log n)\)
std::unordered_maptablica asocjacyjna oparta o haszowanie, średnio \(O(1)\)
std::setzbiór unikalnych elementów, sortowany
std::stack, std::queuestos, kolejka (na bazie innych kontenerów)

Przykład użycia

#include <vector>
#include <algorithm>

std::vector<int> v = {5, 3, 1, 4, 2};
std::sort(v.begin(), v.end());        // sortowanie przez iteratory
for (int x : v) std::cout << x << " ";  // 1 2 3 4 5

Iteratory

Uniwersalny, spójny sposób przechodzenia po elementach różnych kontenerów (begin()/end()) — dzięki temu te same algorytmy (sort, find, for_each...) działają na wielu różnych strukturach danych bez modyfikacji.

STL to klasyczny przykład programowania generycznego (szablony/templates) w C++ — kontenery i algorytmy są niezależne od konkretnego typu danych, ten sam std::vector może przechowywać int, double, obiekty własnych klas itd.

9. Szablony (templates)

Mechanizm programowania generycznego — pisanie funkcji/klas niezależnych od konkretnego typu danych, z którym będą używane. Kompilator generuje konkretną wersję kodu dla każdego użytego typu (w czasie kompilacji).

Szablon funkcji

template <typename T>
T maksimum(T a, T b) {
    return (a > b) ? a : b;
}

int a = maksimum(3, 7);        // T = int
double b = maksimum(2.5, 1.2); // T = double
std::string c = maksimum(std::string("abc"), std::string("xyz")); // T = std::string

Kompilator sam wnioskuje typ T na podstawie argumentów wywołania (nie trzeba pisać maksimum<int>(3,7), choć można jawnie).

Szablon klasy

template <typename T>
class Stos {
    std::vector<T> dane;
public:
    void push(T x) { dane.push_back(x); }
    T pop() {
        T x = dane.back();
        dane.pop_back();
        return x;
    }
    bool pusty() { return dane.empty(); }
};

Stos<int> s1;          // Stos przechowujący int
Stos<std::string> s2; // Stos przechowujący stringi — ten sam kod klasy!

Szablony z wieloma parametrami

template <typename K, typename V>
class Para {
public:
    K klucz;
    V wartosc;
};

Para<std::string, int> p = {"wiek", 25};

Parametry niebędące typami

template <typename T, int ROZMIAR>
class TablicaStala {
    T dane[ROZMIAR];
public:
    int rozmiar() { return ROZMIAR; }
};

TablicaStala<int, 10> t;   // rozmiar jako parametr szablonu, znany w czasie kompilacji
Cała biblioteka STL (patrz punkt 8) jest zbudowana na szablonach — std::vector<int>, std::vector<std::string> to w rzeczywistości dwie różne, wygenerowane przez kompilator klasy z tego samego szablonu std::vector<T>.

Specjalizacja szablonu

Można podać osobną implementację szablonu dla konkretnego typu, jeśli ogólna wersja nie jest dla niego odpowiednia (np. inne zachowanie dla bool niż dla innych typów).

10. Wielodziedziczenie i problem diamentu

Wielodziedziczenie (multiple inheritance)

Klasa w C++ może dziedziczyć jednocześnie po wielu klasach bazowych (w odróżnieniu np. od Javy, gdzie klasa dziedziczy tylko po jednej klasie, choć implementuje wiele interfejsów):

class Latajacy {
public:
    void lec() { std::cout << "Lecę\n"; }
};

class Plywajacy {
public:
    void plyn() { std::cout << "Płynę\n"; }
};

class Kaczka : public Latajacy, public Plywajacy {
    // dziedziczy metody z obu klas
};

Kaczka k;
k.lec();   // z Latajacy
k.plyn();  // z Plywajacy

Problem diamentu (diamond problem)

Powstaje, gdy klasa dziedziczy po dwóch klasach, które same dziedziczą po tej samej, wspólnej klasie bazowej — schemat przypomina diament:

        Zwierze
        /      \
     Ptak      Ssak
        \      /
        Nietoperz
class Zwierze { public: int wiek; };
class Ptak : public Zwierze {};
class Ssak : public Zwierze {};
class Nietoperz : public Ptak, public Ssak {};

Nietoperz n;
// n.wiek = 5;   // BŁĄD: niejednoznaczność! Które "wiek" — z Ptak czy z Ssak?
n.Ptak::wiek = 5; // trzeba jawnie wskazać, z której ścieżki dziedziczenia

Problem: Nietoperz zawiera dwie niezależne kopie pól z Zwierze (jedną przez Ptak, drugą przez Ssak) — odwołanie do wiek jest niejednoznaczne.

Rozwiązanie — dziedziczenie wirtualne (virtual)

class Zwierze { public: int wiek; };
class Ptak : virtual public Zwierze {};
class Ssak : virtual public Zwierze {};
class Nietoperz : public Ptak, public Ssak {};

Nietoperz n;
n.wiek = 5;   // OK! Tylko JEDNA, współdzielona kopia Zwierze

virtual przy dziedziczeniu zapewnia, że niezależnie od tego, przez ile "ścieżek" klasa pochodna dziedziczy po tej samej klasie bazowej, istnieje tylko jedna, współdzielona jej kopia w pamięci obiektu.

Wielodziedziczenie bywa krytykowane za zwiększanie złożoności (właśnie przez problemy jak diamond problem) — część języków (Java, C#) celowo je ograniczyła do jednej klasy bazowej + wielu interfejsów, żeby uniknąć tej niejednoznaczności w ogóle.
