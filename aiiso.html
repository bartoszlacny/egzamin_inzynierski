Administracja i integracja systemów operacyjnych

1. Etapy bootowania systemu operacyjnego

Ogólna sekwencja (Linux, BIOS/legacy)

  1. POST (Power-On Self-Test) — sprzętowy test podstawowych komponentów (RAM, CPU) wykonywany przez firmware płyty głównej
  2. BIOS/UEFI — firmware inicjalizuje sprzęt, odnajduje urządzenie startowe, przekazuje kontrolę dalej
  3. MBR/GPT + bootloader (np. GRUB) — mały program wskazujący, jaki kernel wczytać i z jakimi parametrami; wyświetla menu wyboru systemu/wersji kernela, jeśli skonfigurowano więcej niż jedną opcję
  4. wczytanie jądra (kernel) — kernel Linuksa jest ładowany do pamięci wraz z initramfs/initrd (minimalny system plików z niezbędnymi sterownikami do zamontowania rzeczywistego dysku)
  5. init / systemd (PID 1) — pierwszy proces użytkownika, uruchamia kolejne usługi systemowe (sieć, logowanie, itd.) zgodnie ze zdefiniowanymi zależnościami (jednostkami systemd) lub poziomami uruchomienia (runlevels — starszy System V init)
  6. uruchomienie usług i menedżera logowania — system dochodzi do stanu gotowości (konsola tekstowa albo graficzny ekran logowania)

BIOS vs UEFI

BIOS (legacy)UEFI
Tablica partycjiMBR (max. 4 partycje podstawowe, dysk do 2TB)GPT (dużo więcej partycji, dyski >2TB)
Interfejstekstowy, ograniczonygraficzny, bardziej rozbudowany, wsparcie dla myszy
BezpieczeństwobrakSecure Boot — weryfikacja podpisu cyfrowego bootloadera

systemd — jednostki (units) i cele (targets)

Nowoczesne dystrybucje Linuksa (np. Ubuntu, Fedora, Debian) używają systemd jako systemu init — usługi definiowane jako jednostki (.service), z zależnościami między nimi, grupowane w targets (odpowiedniki starych runlevels, np. multi-user.target, graphical.target).

systemctl status              # status usług
systemctl list-units --type=service
journalctl -b                 # logi z bieżącego bootowania

Bootowanie Windows (skrótowo)

UEFI/BIOS → Windows Boot Manager (bootmgr) → wczytanie winload.exe i jądra (ntoskrnl.exe) → inicjalizacja sterowników i usług → menedżer logowania.

Typowe pytanie: uszereguj podane etapy bootowania w poprawnej kolejności, albo wyjaśnij różnicę między MBR a GPT / BIOS a UEFI.

2. Konfiguracja serwera SSH (sshd)

SSH — podstawy

Protokół (i usługa sshd) do bezpiecznego, szyfrowanego zdalnego dostępu do terminala — zastąpił niezaszyfrowane, starsze protokoły jak Telnet.

Plik konfiguracyjny — /etc/ssh/sshd_config

Port 22                      # port, na którym nasłuchuje serwer (zmiana utrudnia automatyczne skanowanie)
PermitRootLogin no           # zablokowanie logowania bezpośrednio jako root (dobra praktyka bezpieczeństwa)
PasswordAuthentication no    # wyłączenie logowania hasłem — wymusza uwierzytelnianie kluczem
PubkeyAuthentication yes     # zezwolenie na logowanie kluczem publicznym
AllowUsers jan anna          # ograniczenie logowania tylko do wskazanych użytkowników
MaxAuthTries 3               # limit liczby prób uwierzytelnienia

Po zmianie konfiguracji: systemctl restart sshd (żeby zmiany zaczęły działać).

Uwierzytelnianie kluczem publicznym

# na kliencie — generowanie pary kluczy
ssh-keygen -t ed25519

# skopiowanie klucza publicznego na serwer
ssh-copy-id uzytkownik@serwer

# logowanie (bez podawania hasła, jeśli klucz skonfigurowany)
ssh uzytkownik@serwer

Klucz prywatny pozostaje wyłącznie na komputerze klienta (nigdy się go nie udostępnia!), klucz publiczny trafia do pliku ~/.ssh/authorized_keys na serwerze.

Dlaczego klucz jest bezpieczniejszy niż hasło

  • odporny na atak brute-force (klucz kryptograficzny, nie krótkie hasło do odgadnięcia)
  • authorized_keys)

Tunelowanie SSH i przekazywanie portów

ssh -L 8080:localhost:80 serwer     # tunel lokalny — dostęp do usługi na serwerze przez lokalny port
ssh -D 1080 serwer                  # tunel SOCKS — proxy przez SSH
Podstawowa checklist "utwardzania" (hardening) SSH: zmiana domyślnego portu, wyłączenie logowania jako root, wyłączenie logowania hasłem (tylko klucze), ograniczenie listy dozwolonych użytkowników, ewentualnie fail2ban do automatycznego blokowania adresów IP po nieudanych próbach logowania.

3. Układy dysków RAID

RAID (Redundant Array of Independent Disks) — sposób łączenia wielu fizycznych dysków w jeden logiczny wolumen, dla zwiększenia wydajności i/lub odporności na awarię pojedynczego dysku.

PoziomZasadaOdporność na awarięWykorzystanie pojemności
RAID 0 (stripowanie) dane dzielone (stripe) na wiele dysków, zapis/odczyt równolegle brak — awaria jednego dysku = utrata wszystkich danych 100% (suma wszystkich dysków)
RAID 1 (mirroring) pełna kopia (mirror) danych na każdym dysku przetrwa awarię wszystkich dysków poza jednym 50% (dla 2 dysków) — reszta to duplikat
RAID 5 stripowanie danych + rozproszona parzystość (parity) na wszystkich dyskach przetrwa awarię jednego dysku \((n-1)/n\) — jeden dysk "efektywnie" na parzystość
RAID 6 jak RAID 5, ale z podwójną parzystością przetrwa awarię dwóch dysków \((n-2)/n\)
RAID 10 (1+0) zestaw par mirror (RAID 1), połączonych stripingiem (RAID 0) przetrwa awarię wielu dysków (o ile nie obu z tej samej pary) 50%

Parzystość (parity) w RAID 5/6

Dodatkowe dane obliczone (najczęściej operacją XOR) z danych na innych dyskach — pozwalają odtworzyć zawartość uszkodzonego dysku na podstawie parzystości i pozostałych, sprawnych dysków.

RAID sprzętowy vs programowy

  • sprzętowy — dedykowany kontroler RAID wykonuje obliczenia (np. parzystość) niezależnie od CPU systemu
  • programowy — RAID zarządzany przez system operacyjny (np. mdadm w Linuksie), obciąża CPU hosta, ale bardziej elastyczny i tańszy

RAID a backup

RAID nie jest substytutem backupu! Chroni przed awarią fizyczną dysku, ale nie przed przypadkowym usunięciem plików, błędem użytkownika, ransomware czy błędem w samym systemie plików — te problemy replikują się na wszystkie dyski RAID identycznie.

Wybór poziomu — kompromis

RAID 0 — maksymalna wydajność, zero bezpieczeństwa (np. dane tymczasowe, cache). RAID 1 — prostota i bezpieczeństwo, kosztem pojemności. RAID 5/6 — dobry kompromis pojemność/bezpieczeństwo dla większej liczby dysków, ale wolniejszy zapis (obliczanie parzystości) i długi czas odbudowy (rebuild) po awarii.

4. Logiczne wolumeny dyskowe (LVM)

LVM (Logical Volume Manager) — warstwa abstrakcji między fizycznymi dyskami a systemami plików, pozwalająca elastycznie zarządzać przestrzenią dyskową bez sztywnego przywiązania do fizycznych partycji.

Hierarchia LVM

PoziomNazwaOpis
1PV (Physical Volume)fizyczna partycja/dysk przygotowany do użycia przez LVM
2VG (Volume Group)"pula" przestrzeni złożona z jednego lub wielu PV — traktowana jako jeden duży zbiór dostępnej pamięci
3LV (Logical Volume)"wirtualna partycja" wykrojona z VG — na niej dopiero tworzy się system plików
PV (dysk1) ┐
PV (dysk2) ├─→ VG (grupa1) ─┬─→ LV (root) → system plików ext4
PV (dysk3) ┘                 ├─→ LV (home) → system plików ext4
                              └─→ LV (dane) → system plików xfs

Podstawowe komendy

pvcreate /dev/sdb1              # oznacz partycję jako Physical Volume
vgcreate grupa1 /dev/sdb1        # utwórz Volume Group z PV
lvcreate -L 10G -n dane grupa1   # utwórz Logical Volume 10GB w grupa1
mkfs.ext4 /dev/grupa1/dane       # utwórz system plików na LV

Kluczowa zaleta — elastyczność

  • zmiana rozmiaru "w locie" — LV można powiększyć (lvextend) lub (ostrożniej) zmniejszyć bez przenoszenia danych na inny fizyczny dysk, o ile w VG jest dostępna wolna przestrzeń
  • rozciąganie na wiele dysków — VG może obejmować wiele fizycznych dysków, LV może "rozlać się" na nie wszystkie, ułatwiając dodawanie przestrzeni bez zmiany struktury partycji
  • snapshoty — LVM pozwala zrobić migawkę (snapshot) stanu LV w danym momencie — przydatne do backupów "na żywo" bez zatrzymywania systemu

LVM vs zwykłe partycjonowanie

Partycje "klasyczne"LVM
Zmiana rozmiarutrudna, często wymaga przenoszenia danychłatwa, "w locie" (przy wolnym miejscu w VG)
Rozciąganie na wiele dyskównie (partycja jest ograniczona do jednego dysku, poza RAID)tak, natywnie
Złożonośćprostsza koncepcyjniedodatkowa warstwa abstrakcji do zrozumienia
Typowe pytanie: opisz kroki potrzebne do powiększenia partycji /home zarządzanej przez LVM o dodatkowe 20GB, zakładając wolne miejsce w Volume Group.

5. Zarządzanie systemami plików i użytkownikami

Montowanie systemów plików (Linux)

mount /dev/sdb1 /mnt/dane          # ręczne zamontowanie
umount /mnt/dane                   # odmontowanie

# /etc/fstab — automatyczne montowanie przy starcie systemu
/dev/sdb1   /mnt/dane   ext4   defaults   0   2

Uprawnienia do plików (Linux)

-rwxr-xr--  1 jan  grupa  1024  plik.txt

Trzy grupy uprawnień: właściciel (owner), grupa (group), inni (others) — każda z prawami read (odczyt), write (zapis), execute (wykonanie):

chmod 754 plik.txt      # 7=rwx (właściciel), 5=r-x (grupa), 4=r-- (inni)
chmod u+x plik.txt      # dodanie prawa wykonania właścicielowi
chown jan:grupa plik.txt  # zmiana właściciela i grupy

Zarządzanie użytkownikami i grupami (Linux)

useradd -m -s /bin/bash jan     # nowy użytkownik (-m: utwórz katalog domowy)
passwd jan                      # ustawienie hasła
usermod -aG sudo jan             # dodanie do grupy (np. sudo — uprawnienia administracyjne)
userdel -r jan                   # usunięcie użytkownika (-r: wraz z katalogiem domowym)

groupadd deweloperzy
groups jan                       # lista grup, do których należy jan

Pliki systemowe: /etc/passwd (lista użytkowników i podstawowe dane), /etc/shadow (zahaszowane hasła), /etc/group (definicje grup).

Model uprawnień — sudo vs root

Zamiast logować się jako root na stałe (ryzykowne — każdy błąd/awaria ma pełne uprawnienia), standardowa praktyka to praca jako zwykły użytkownik i używanie sudo do pojedynczych komend wymagających podniesionych uprawnień — z pełnym logowaniem, kto i kiedy użył jakiego polecenia z podniesieniem uprawnień.

Zarządzanie użytkownikami (Windows, dla porównania)

net user jan HasloTest /add
net localgroup Administratorzy jan /add

Koncepcyjnie analogiczne mechanizmy: konta użytkowników, grupy, uprawnienia NTFS do plików/folderów (odczyt, zapis, modyfikacja, pełna kontrola).

Systemy plików — wybór i zarządzanie

Formatowanie: mkfs.ext4, mkfs.xfs (Linux), sprawdzanie/naprawa: fsck (patrz przedmiot Wprowadzenie do systemów operacyjnych — organizacja systemów plików).

Typowe zadanie: dla podanych uprawnień w formie rwxr-x--- zdekoduj, co może zrobić właściciel/grupa/inni, albo napisz polecenie chmod/chown realizujące opisane słownie wymaganie dostępu.

6. Wirtualizacja i konteneryzacja

Maszyny wirtualne (VM)

Program (hipervizor) emuluje kompletny wirtualny komputer — z własnym, pełnym systemem operacyjnym (kernelem), na którym działają aplikacje, tak jak na fizycznej maszynie.

Typ hipervizoraZasadaPrzykłady
Typ 1 (bare-metal)działa bezpośrednio na sprzęcie, bez systemu-hosta pod sobąVMware ESXi, Microsoft Hyper-V, KVM
Typ 2 (hosted)działa jako aplikacja na "zwykłym" systemie operacyjnymVirtualBox, VMware Workstation

Kontenery (np. Docker)

Izolują procesy aplikacji na poziomie systemu operacyjnego — kontenery współdzielą jądro systemu-hosta (nie ma osobnego kernela w każdym kontenerze), pakując tylko aplikację i jej zależności (biblioteki, konfigurację).

VM vs kontener — porównanie

Maszyna wirtualnaKontener
Jądro systemuwłasne, pełne (w każdej VM)współdzielone z hostem
Rozmiarduży (GB) — cały system operacyjnymały (MB) — tylko aplikacja + zależności
Czas startusekundy/minuty (boot całego OS)ułamki sekundy (start procesu)
Izolacjasilna (pełna, na poziomie sprzętu wirtualnego)słabsza (na poziomie procesów/przestrzeni nazw jądra)
Można różne systemy na hoście?tak (np. Windows VM na Linux hoście)nie — kontener wymaga zgodności z jądrem hosta (Linux kontenery na Linux hoście)

Podstawowe komendy Docker

docker build -t mojaapp .          # zbudowanie obrazu z Dockerfile
docker run -d -p 8080:80 mojaapp    # uruchomienie kontenera w tle, mapowanie portu
docker ps                           # lista działających kontenerów
docker exec -it <id> bash          # wejście do działającego kontenera
docker stop <id>

Obraz vs kontener

Obraz (image) — statyczny, tylko-do-odczytu "szablon" (jak klasa) zawierający aplikację i jej środowisko; kontener — działająca instancja obrazu (jak obiekt) — z tego samego obrazu można uruchomić wiele niezależnych kontenerów.

Orkiestracja kontenerów

Przy wielu kontenerach (mikroserwisy — patrz przedmiot Projektowanie aplikacji internetowych) potrzebne narzędzia zarządzające ich cyklem życia na wielu maszynach — np. Kubernetes, Docker Compose (dla prostszych, jednomaszynowych scenariuszy).

Typowe pytanie: kiedy wybrać VM, a kiedy kontener — VM gdy potrzeba pełnej izolacji/innego systemu operacyjnego (np. hostowanie wielu klientów na jednym serwerze fizycznym); kontener gdy liczy się szybkość, gęstość upakowania i łatwa przenośność tej samej aplikacji między środowiskami (dev/test/produkcja).

7. Automatyzacja zadań administracyjnych

cron (Linux) — harmonogram zadań

Demon systemowy wykonujący zadania w zaplanowanych momentach, zdefiniowanych w plikach crontab:

crontab -e     # edycja crontab bieżącego użytkownika
crontab -l     # wyświetlenie aktualnych zaplanowanych zadań

Składnia crontab

# minuta godzina dzień_miesiąca miesiąc dzień_tygodnia   komenda
0    2      *              *       *                /skrypty/backup.sh
*/15 *      *              *       *                /skrypty/sprawdz_dysk.sh
0    0      1              *       *                /skrypty/raport_miesieczny.sh
30   8      *              *       1-5               /skrypty/powiadomienie.sh
PoleZakres
minuta0-59
godzina0-23
dzień miesiąca1-31
miesiąc1-12
dzień tygodnia0-6 (0 = niedziela)

* oznacza "każdy" (dowolna wartość), */15 — "co 15 jednostek", 1-5 — zakres.

systemd timers — nowocześniejsza alternatywa

W dystrybucjach z systemd zadania okresowe można definiować przez parę plików: jednostka .service (co wykonać) + jednostka .timer (kiedy wykonać):

# /etc/systemd/system/backup.timer
[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
systemctl enable --now backup.timer
systemctl list-timers          # lista zaplanowanych timerów

cron vs systemd timers

cronsystemd timers
Prostotabardzo prosta, jedna liniawymaga dwóch plików (.service + .timer)
Logowanieograniczone (zależnie od konfiguracji)zintegrowane z journalctl — pełne logi
Zależności między zadaniamibrak natywnego wsparciamożna wykorzystać mechanizm zależności jednostek systemd
Uruchomienie "zaległego" zadania po restarcienie (jeśli system był wyłączony w zaplanowanym momencie, zadanie przepada)tak, z opcją Persistent=true

Typowe zastosowania automatyzacji

automatyczne backupy (nawiązanie do RAID z punktu 3 — RAID nie zastępuje backupu, ale cron/systemd timer może go zautomatyzować), czyszczenie starych logów/plików tymczasowych, okresowe raporty/monitoring, odnawianie certyfikatów (np. Let's Encrypt), aktualizacje systemu w oknie serwisowym.

Typowe zadanie: napisz wpis crontab wykonujący dany skrypt co godzinę w dni robocze, albo w każdą niedzielę o 3:00 w nocy — trzeba poprawnie rozpisać pola minuta/godzina/dzień_miesiąca/miesiąc/dzień_tygodnia.
