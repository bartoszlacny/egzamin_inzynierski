Wstęp do programowania w języku Java

1. Polimorfizm

Możliwość traktowania obiektów różnych klas (powiązanych dziedziczeniem/interfejsem) jednolicie, przez referencję do typu bazowego, przy czym faktycznie wykonana zostaje metoda właściwa dla rzeczywistego typu obiektu.

class Zwierze {
    void wydajDzwiek() { System.out.println("..."); }
}
class Pies extends Zwierze {
    @Override
    void wydajDzwiek() { System.out.println("Hau!"); }
}
class Kot extends Zwierze {
    @Override
    void wydajDzwiek() { System.out.println("Miau!"); }
}

Zwierze[] zwierzeta = { new Pies(), new Kot() };
for (Zwierze z : zwierzeta) {
    z.wydajDzwiek();   // "Hau!", potem "Miau!" — mimo że typ zmiennej to Zwierze
}

Polimorfizm w czasie wykonania (dynamic dispatch)

W Javie wywołania metod niestatycznych są domyślnie polimorficzne — o tym, która wersja metody się wykona, decyduje rzeczywisty typ obiektu w czasie wykonania, nie zadeklarowany typ zmiennej (to odróżnia Javę od C++, gdzie trzeba jawnie oznaczyć metodę jako virtual).

Polimorfizm parametryczny (przeciążenie) vs polimorfizm dziedziczenia

  • polimorfizm przez dziedziczenie (nadpisywanie) — jak w przykładzie wyżej, rozstrzygany w czasie wykonania
  • polimorfizm przez przeciążanie (overloading) — wiele metod o tej samej nazwie, różne parametry, rozstrzygane w czasie kompilacji na podstawie typów argumentów

Upcasting i downcasting

Zwierze z = new Pies();          // upcasting — zawsze bezpieczny, niejawny
Pies p = (Pies) z;                // downcasting — wymaga jawnego rzutowania, może zgłosić ClassCastException
Polimorfizm to fundament pisania kodu działającego na poziomie abstrakcji klasy bazowej/interfejsu (np. metoda przyjmująca List<T> działa identycznie niezależnie, czy dostanie ArrayList czy LinkedList) — kluczowy mechanizm dla elastycznego, rozszerzalnego kodu.

2. Mechanizm nadpisywania metod (overriding)

Zasady nadpisywania

Klasa pochodna może dostarczyć własną implementację metody zdefiniowanej w klasie bazowej — musi mieć:

  • taką samą nazwę i listę parametrów (sygnaturę)
  • taki sam lub bardziej specyficzny (kowariantny) typ zwracany
  • taki sam lub szerszy poziom dostępu (nie można zwężyć np. z public na private)

Adnotacja @Override

@Override
void wydajDzwiek() { ... }

Nieobowiązkowa, ale zalecana — kompilator sprawdza, czy metoda faktycznie nadpisuje coś z klasy bazowej; jeśli literówka w nazwie/sygnaturze spowoduje, że to wcale nie jest nadpisanie (a nowa, osobna metoda), kompilator zgłosi błąd zamiast pozwolić na trudny do wykrycia błąd logiczny.

Wywołanie metody klasy bazowej — super

class Pies extends Zwierze {
    @Override
    void wydajDzwiek() {
        super.wydajDzwiek();   // wywołanie oryginalnej implementacji z Zwierze
        System.out.println("Hau!");
    }
}

Nadpisywanie vs przesłanianie (overriding vs hiding)

Metody statyczne nie są polimorficzne — jeśli klasa pochodna definiuje metodę statyczną o tej samej sygnaturze, to nie jest nadpisanie, lecz przesłonięcie (hiding) — wybór metody odbywa się na podstawie zadeklarowanego typu zmiennej (czas kompilacji), nie rzeczywistego typu obiektu.

Metody i klasy final

final przy metodzie — zakazuje jej nadpisania w klasach pochodnych; final przy klasie — zakazuje dziedziczenia po niej w ogóle (np. String jest klasą final).

Konstruktory — nie są nadpisywane

Konstruktory nie dziedziczą się i nie są nadpisywane jak zwykłe metody — każda klasa definiuje własne, choć może wywołać konstruktor klasy bazowej przez super(...) (musi to być pierwsza instrukcja w konstruktorze pochodnym).

Klasyczne pytanie: różnica między overloading (przeciążanie — te same nazwy, różne parametry, rozstrzygane statycznie) i overriding (nadpisywanie — ta sama sygnatura w klasie pochodnej, rozstrzygane dynamicznie w czasie wykonania).

Cechy typów prymitywnych

  • przechowują wartość bezpośrednio (nie referencję) — zmienna to "kontener" z konkretną liczbą/znakiem
  • int)
  • wartość

Typy obiektowe (referencyjne)

Klasy, interfejsy, tablice — zmienna przechowuje referencję (adres) do obiektu na stercie, nie samą wartość:

String s1 = new String("abc");
String s2 = s1;      // s2 wskazuje na TEN SAM obiekt co s1
// przypisanie/przekazanie kopiuje REFERENCJĘ, nie zawartość obiektu

Klasy opakowujące (wrapper classes)

Każdy typ prymitywny ma odpowiadającą klasę obiektową: int→Integer, double→Double, boolean→Boolean, char→Character itd. — potrzebne np. w kolekcjach generycznych (patrz punkt 5), które przechowują tylko obiekty, nie typy prymitywne.

Autoboxing i unboxing

Integer obj = 5;        // autoboxing: int → Integer (automatyczne)
int x = obj;             // unboxing: Integer → int (automatyczne)

List<Integer> lista = new ArrayList<>();
lista.add(10);            // 10 (int) automatycznie "boxowane" do Integer
Pułapka: porównywanie obiektów Integer operatorem == porównuje referencje, nie wartości (poza małym zakresem cache'owanym przez JVM, -128 do 127) — do porównania wartości należy używać .equals(). Typy prymitywne (int) porównywane == porównują wartości bezpośrednio — częste źródło błędów dla początkujących.

4. Interfejsy i interfejsy funkcyjne

Interfejs — kontrakt

Definiuje zestaw metod, które implementująca klasa musi zaimplementować, bez (zwykle) podawania samej implementacji:

interface Ksztalt {
    double pole();          // metoda abstrakcyjna (domyślnie)
}

class Kwadrat implements Ksztalt {
    double bok;
    Kwadrat(double b) { bok = b; }
    public double pole() { return bok * bok; }
}

Klasa może implementować wiele interfejsów

class Kaczka implements Latajacy, Plywajacy { ... }

W odróżnieniu od dziedziczenia klas (Java zezwala tylko na jedną klasę bazową), interfejsów można implementować wiele naraz — to sposób Javy na uniknięcie problemu diamentu z wielodziedziczenia (patrz przedmiot Programowanie obiektowe/C++).

Metody domyślne (default) i statyczne w interfejsach

interface Ksztalt {
    double pole();
    default void wypisz() {           // metoda z domyślną implementacją
        System.out.println("Pole: " + pole());
    }
    static Ksztalt punkt() {           // metoda statyczna interfejsu
        return () -> 0;
    }
}

Pozwala dodawać nowe metody do istniejącego interfejsu bez łamania klas, które go już implementują (nie muszą dostarczać implementacji metody default, jeśli domyślna im wystarcza).

Interfejsy funkcyjne

Interfejs z dokładnie jedną metodą abstrakcyjną — może być reprezentowany przez wyrażenie lambda:

@FunctionalInterface
interface Operacja {
    int wykonaj(int a, int b);
}

Operacja dodaj = (a, b) -> a + b;   // implementacja przez lambdę
System.out.println(dodaj.wykonaj(2,3));  // 5

Adnotacja @FunctionalInterface jest opcjonalna, ale wymusza kompilacyjną weryfikację, że interfejs ma tylko jedną metodę abstrakcyjną.

Wbudowane interfejsy funkcyjne (java.util.function)

InterfejsSygnaturaZastosowanie
Function<T,R>R apply(T t)przekształcenie wartości typu T na R
Predicate<T>boolean test(T t)warunek logiczny (np. filtrowanie)
Consumer<T>void accept(T t)"zużywa" wartość, nic nie zwraca (np. wypisanie)
Supplier<T>T get()dostarcza wartość bez argumentów
List<Integer> lista = List.of(1,2,3,4,5);
lista.stream()
     .filter(x -> x % 2 == 0)     // Predicate
     .map(x -> x * x)              // Function
     .forEach(System.out::println); // Consumer
Interfejsy funkcyjne + lambdy to podstawa API Stream w Javie — pozwalają pisać zwięzły, "funkcyjny" styl przetwarzania kolekcji, zamiast klasycznych pętli.

5. Typy generyczne

Mechanizm pozwalający pisać klasy/metody niezależne od konkretnego typu danych, z zachowaniem bezpieczeństwa typów sprawdzanego w czasie kompilacji.

Przed generykami (Java <5, tylko historycznie)

List lista = new ArrayList();    // brak informacji o typie elementów
lista.add("tekst");
lista.add(5);                     // kompiluje się, ale to błąd logiczny!
String s = (String) lista.get(1); // ClassCastException w czasie WYKONANIA

Z generykami

List<String> lista = new ArrayList<>();
lista.add("tekst");
// lista.add(5);      // BŁĄD KOMPILACJI — wykryte od razu, nie w czasie wykonania!
String s = lista.get(0);  // bez rzutowania — kompilator wie, że to String

Klasa generyczna

class Pojemnik<T> {
    private T zawartosc;
    public void ustaw(T x) { zawartosc = x; }
    public T pobierz() { return zawartosc; }
}

Pojemnik<Integer> p1 = new Pojemnik<>();
p1.ustaw(5);
Pojemnik<String> p2 = new Pojemnik<>();
p2.ustaw("tekst");

Metoda generyczna

static <T> T pierwszy(List<T> lista) {
    return lista.get(0);
}

Wiele parametrów typu

class Para<K, V> {
    K klucz; V wartosc;
    Para(K k, V v) { klucz = k; wartosc = v; }
}

Para<String, Integer> p = new Para<>("wiek", 25);

Ograniczenia typu (bounded types)

class Liczbowy<T extends Number> {   // T musi być podtypem Number (Integer, Double...)
    T wartosc;
    double podwojna() { return wartosc.doubleValue() * 2; }
}

Wildcards — ?

void wypisz(List<?> lista) { ... }                  // dowolny typ elementów
void sumuj(List<? extends Number> lista) { ... }     // Number lub jego podtyp (tylko odczyt bezpieczny)

Wymazywanie typów (type erasure)

W czasie wykonania informacja o parametrze generycznym jest "wymazywana" — JVM nie wie w runtime, czy to był List<String> czy List<Integer> (obie stają się po kompilacji zwykłym List). Generyki to więc mechanizm czasu kompilacji (bezpieczeństwo typów, brak rzutowań w kodzie źródłowym), nie realna specjalizacja kodu w czasie wykonania (w odróżnieniu np. od szablonów C++, które generują osobny kod dla każdego typu).

Konsekwencja wymazywania typów: nie można sprawdzić instanceof List<String> ani utworzyć tablicy generycznej new T[10] — te operacje wymagałyby informacji o typie, która w runtime już nie istnieje.

6. Wyjątki w Javie

Hierarchia wyjątków

Throwable
├── Error               (błędy krytyczne JVM — np. OutOfMemoryError; nie łapie się ich zwykle)
└── Exception
    ├── RuntimeException (unchecked — np. NullPointerException, ArrayIndexOutOfBoundsException)
    └── (pozostałe)       (checked — np. IOException)

Checked vs unchecked

CheckedUnchecked (RuntimeException)
Wymuszenie przez kompilatortak — musisz obsłużyć (try/catch) lub zadeklarować (throws)nie — kompiluje się nawet bez obsługi
Typowa przyczynaproblemy zewnętrzne, przewidywalne (brak pliku, błąd sieci)błędy programistyczne (null, złe indeksowanie)
PrzykładyIOException, SQLExceptionNullPointerException, ArithmeticException, ClassCastException

try / catch / finally

try {
    int[] tab = new int[5];
    System.out.println(tab[10]);   // rzuci ArrayIndexOutOfBoundsException
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Błąd indeksu: " + e.getMessage());
} catch (Exception e) {
    System.out.println("Inny błąd: " + e.getMessage());
} finally {
    System.out.println("Wykonuje się zawsze");
}

Deklaracja throws — propagacja wyjątku checked

void wczytajPlik(String nazwa) throws IOException {
    FileReader f = new FileReader(nazwa);   // może rzucić IOException
    // ...
}

void wywolaj() {
    try {
        wczytajPlik("dane.txt");
    } catch (IOException e) {
        System.out.println("Nie udało się wczytać pliku");
    }
}

Try-with-resources

try (FileReader f = new FileReader("dane.txt")) {
    // f automatycznie zamknięty na końcu bloku, nawet przy wyjątku
} catch (IOException e) {
    e.printStackTrace();
}

Wymaga, by zasób implementował interfejs AutoCloseable — analogiczne do with w Pythonie (patrz przedmiot Języki skryptowe).

Własne wyjątki

class NiewystarczajaceSaldoException extends Exception {
    public NiewystarczajaceSaldoException(String wiadomosc) {
        super(wiadomosc);
    }
}

void wyplac(double kwota) throws NiewystarczajaceSaldoException {
    if (kwota > saldo) {
        throw new NiewystarczajaceSaldoException("Brak środków");
    }
}
Dobra praktyka: dziedzicz własne wyjątki po Exception (checked) tylko gdy wołający powinien być zmuszony do obsługi błędu; jeśli to raczej błąd programistyczny (np. niepoprawny argument), lepiej po RuntimeException (unchecked).

7. Kolekcje (Collections Framework)

Hierarchia głównych interfejsów

InterfejsCechaPopularne implementacje
List<T>uporządkowana, dopuszcza duplikaty, dostęp po indeksieArrayList, LinkedList
Set<T>unikalne elementy, brak dostępu po indeksieHashSet, TreeSet, LinkedHashSet
Map<K,V>mapowanie klucz→wartość, unikalne kluczeHashMap, TreeMap, LinkedHashMap
Queue<T>FIFO (lub priorytetowa)LinkedList, PriorityQueue
Deque<T>kolejka dwustronna (i jako stos)ArrayDeque

ArrayList vs LinkedList

Analogiczne do tablicy dynamicznej vs listy z dowiązaniami (patrz przedmiot Algorytmy i struktury danych): ArrayList — szybki dostęp po indeksie \(O(1)\), wolniejsze wstawianie w środku \(O(n)\); LinkedList — odwrotnie.

HashMap vs TreeMap

  • HashMap — oparta o tablicę haszującą, brak gwarantowanej kolejności, operacje średnio \(O(1)\)
  • TreeMap — oparta o drzewo (czerwono-czarne), klucze sortowane, operacje \(O(\log n)\)
  • LinkedHashMap — zachowuje kolejność wstawiania elementów, kosztem niewielkiego narzutu względem HashMap

Przykład użycia

Map<String, Integer> wiek = new HashMap<>();
wiek.put("Jan", 25);
wiek.put("Anna", 30);

for (Map.Entry<String, Integer> wpis : wiek.entrySet()) {
    System.out.println(wpis.getKey() + ": " + wpis.getValue());
}

List<Integer> lista = new ArrayList<>(List.of(5, 3, 1, 4));
Collections.sort(lista);          // sortowanie w miejscu
lista.stream().filter(x -> x > 2).forEach(System.out::println);

Iterator

Uniwersalny sposób przechodzenia po elementach kolekcji, niezależnie od jej konkretnej implementacji:

Iterator<String> it = lista.iterator();
while (it.hasNext()) {
    String element = it.next();
    if (element.equals("usun")) it.remove();  // bezpieczne usuwanie podczas iteracji
}
Modyfikacja kolekcji "zwykłą" pętlą for-each podczas iteracji (np. lista.remove(x)) rzuca ConcurrentModificationException — do bezpiecznego usuwania w trakcie iteracji trzeba użyć Iterator.remove().

8. Klasy abstrakcyjne vs interfejsy

Klasa abstrakcyjna

abstract class Figura {
    String nazwa;
    Figura(String nazwa) { this.nazwa = nazwa; }   // konstruktor — OK w klasie abstrakcyjnej

    abstract double pole();          // metoda abstrakcyjna — brak implementacji

    void wypisz() {                  // metoda konkretna — WSPÓLNA implementacja dla wszystkich podklas
        System.out.println(nazwa + ": " + pole());
    }
}

class Kwadrat extends Figura {
    double bok;
    Kwadrat(double b) { super("Kwadrat"); bok = b; }
    double pole() { return bok*bok; }
}

// Figura f = new Figura("x");   // BŁĄD — nie można tworzyć instancji klasy abstrakcyjnej

Porównanie

Klasa abstrakcyjnaInterfejs
Dziedziczenie/implementacjatylko jedna (extends)wiele naraz (implements)
Pola z danymi (stan)tak, może mieć dowolne pola instancjitylko stałe (public static final, domyślnie)
Konstruktortak (wywoływany przez super() z podklasy)nie
Metody konkretne (z implementacją)tak, dowolna liczbatak, ale jako default/static (od Java 8)
Poziomy dostępu metoddowolne (public, protected, private)domyślnie public

Kiedy który wybrać?

  • klasa abstrakcyjna — gdy podklasy mają wspólny stan (pola) i/lub dużo wspólnej logiki do odziedziczenia, a tylko część zachowania różni się między nimi ("jest rodzajem X, ale różni się szczegółem")
  • interfejs — gdy chcesz zdefiniować kontrakt/zdolność, którą różne, niepowiązane hierarchią klasy mogą implementować ("umie robić X", niezależnie od tego "czym jest") — pozwala też łączyć wiele niezależnych "zdolności" w jednej klasie
Częsta zasada praktyczna: interfejs, kiedy się da (elastyczność wielokrotnej implementacji), klasa abstrakcyjna, kiedy trzeba (współdzielony stan/konstruktor/dużo wspólnej logiki) — obie techniki nie wykluczają się, klasa może jednocześnie dziedziczyć po klasie abstrakcyjnej i implementować kilka interfejsów.
