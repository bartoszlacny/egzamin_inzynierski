Projektowanie aplikacji internetowych

1. Rodzaje i zastosowanie technologii webowych

Podział aplikacji webowych wg architektury renderowania

TypZasadaZalety/wady
SSR (Server-Side Rendering) serwer generuje gotowy HTML dla każdego żądania szybsze pierwsze wyświetlenie, lepsze SEO; więcej obciążenia serwera, przeładowanie przy każdej akcji
SPA (Single Page Application) jedna strona HTML wczytywana raz, dalsza treść generowana dynamicznie w przeglądarce przez JS (np. React, Vue, Angular) płynne UX (bez przeładowań), ale wolniejsze pierwsze wczytanie, trudniejsze SEO bez dodatkowych technik
SSG (Static Site Generation) strony wygenerowane z wyprzedzeniem (w czasie budowania), serwowane jako statyczne pliki bardzo szybkie, tanie w hostowaniu; nie nadaje się do często zmieniającej się/personalizowanej treści
PWA (Progressive Web App) aplikacja webowa z cechami natywnej apki — działanie offline (service workers), instalacja na urządzeniu, powiadomienia push łączy zasięg strony WWW z doświadczeniem zbliżonym do aplikacji mobilnej

Architektura klient-serwer i API

Nowoczesne aplikacje webowe zwykle rozdzielają frontend (interfejs w przeglądarce) od backendu (logika, baza danych), komunikujące się przez API (najczęściej REST lub GraphQL) — pozwala to na współdzielenie tego samego backendu np. przez aplikację webową i mobilną.

Technologie frontendowe/backendowe (przegląd)

Frontend: HTML/CSS/JS + frameworki (React, Vue, Angular). Backend: różne języki/frameworki (PHP, Node.js/Express, Python/Django/Flask, Java/Spring, .NET) — komunikacja z bazą danych, logika biznesowa (patrz przedmiot Języki hipertekstowe i tworzenie stron WWW dla podstaw PHP/JS).

Architektura mikroserwisów vs monolityczna

  • monolit — cała aplikacja jako jeden, spójny program/proces — prostszy na start, ale trudniej skalować/wdrażać fragmentarycznie
  • mikroserwisy — aplikacja podzielona na małe, niezależne usługi komunikujące się przez API — łatwiejsze skalowanie i niezależny rozwój zespołów, ale większa złożoność operacyjna (komunikacja sieciowa, monitoring wielu usług)

2. Standardy wymiany danych — XML i JSON

JSON (JavaScript Object Notation)

{
    "imie": "Jan",
    "wiek": 25,
    "aktywny": true,
    "hobby": ["sport", "muzyka"],
    "adres": {
        "miasto": "Warszawa",
        "kod": "00-001"
    }
}
  • typy danych: string, number, boolean, null, obiekt ({}), tablica ([])

XML (Extensible Markup Language)

<osoba>
    <imie>Jan</imie>
    <wiek>25</wiek>
    <aktywny>true</aktywny>
    <hobby>sport</hobby>
    <hobby>muzyka</hobby>
    <adres>
        <miasto>Warszawa</miasto>
        <kod>00-001</kod>
    </adres>
</osoba>
  • oparty na znacznikach (tagach), podobnie jak HTML — hierarchiczna struktura drzewa
  • wspiera atrybuty znaczników (<osoba id="1">), przestrzenie nazw (namespaces), oraz walidację struktury przez schematy (DTD, XSD)

Parsowanie i walidacja

JSON — parsowane natywnie w JS (JSON.parse()/JSON.stringify()), w innych językach przez biblioteki (np. w Pythonie moduł json). XML — parsowane przez DOM (całe drzewo w pamięci) albo SAX (strumieniowo, zdarzeniowo, mniej pamięci dla dużych plików).

Typowe pytanie: przekonwertuj dany fragment danych między formatem JSON i XML, albo wskaż, kiedy XML wciąż ma przewagę nad JSON (np. gdy potrzebna jest formalna walidacja struktury przez schemat, albo integracja z systemami korporacyjnymi używającymi SOAP).

3. Bezpieczeństwo i ochrona danych osobowych

Typowe zagrożenia aplikacji webowych

ZagrożenieZasada atakuOchrona
SQL Injection wstrzyknięcie złośliwego kodu SQL przez niesprawdzone dane wejściowe (patrz przedmiot Języki hipertekstowe) zapytania przygotowane (prepared statements), walidacja danych wejściowych
XSS (Cross-Site Scripting) wstrzyknięcie złośliwego skryptu JS wykonywanego w przeglądarce innego użytkownika (np. przez niesprawdzony komentarz na stronie) escapowanie/sanityzacja danych wyświetlanych na stronie, polityka CSP (Content Security Policy)
CSRF (Cross-Site Request Forgery) oszukanie zalogowanego użytkownika, by nieświadomie wykonał żądanie do innej strony (np. kliknięcie złośliwego linku wykonuje akcję na koncie bankowym ofiary) tokeny CSRF (jednorazowe, dowiązane do sesji), sprawdzanie nagłówka Referer/Origin
Atak brute-force na logowanie automatyczne próbowanie wielu kombinacji hasła limitowanie liczby prób, CAPTCHA, blokada konta po wielu nieudanych próbach

Uwierzytelnianie i autoryzacja

  • uwierzytelnianie (authentication) — potwierdzenie tożsamości ("kim jesteś") — login/hasło, dwuczynnikowe (2FA)
  • autoryzacja (authorization) — sprawdzenie uprawnień ("co możesz robić") — role, listy dostępu
  • hashowanie haseł — hasła nigdy nie powinny być przechowywane w bazie w postaci czystego tekstu, tylko jako hash (np. bcrypt, Argon2) — nawet wyciek bazy nie odkrywa bezpośrednio hasła
  • sesje i tokeny (JWT) — po zalogowaniu serwer wydaje token/identyfikator sesji, potwierdzający tożsamość przy kolejnych żądaniach bez ponownego logowania

RODO / GDPR — podstawy ochrony danych osobowych

Ogólne rozporządzenie o ochronie danych (RODO/GDPR) — regulacja UE dotycząca przetwarzania danych osobowych. Kluczowe zasady:

  • minimalizacja danych — zbieranie tylko danych faktycznie potrzebnych do celu przetwarzania
  • zgoda — wyraźna, świadoma zgoda użytkownika na przetwarzanie danych (np. konkretne, niezaznaczone domyślnie checkboxy)
  • prawo do bycia zapomnianym — użytkownik może zażądać usunięcia swoich danych
  • prawo dostępu i przenoszenia danych — użytkownik może zażądać kopii swoich danych w ustrukturyzowanym formacie
  • privacy by design — ochrona prywatności uwzględniana od samego początku projektowania systemu, nie dodawana "na końcu"
  • obowiązek zgłaszania wycieków danych — w określonym czasie od wykrycia naruszenia

Szyfrowanie danych

Dane osobowe (zwłaszcza wrażliwe) powinny być szyfrowane "w tranzycie" (przesyłanie — HTTPS/TLS, patrz przedmiot Sieci komputerowe) i "w spoczynku" (przechowywanie — szyfrowanie bazy danych/dysku), minimalizując ryzyko odczytu danych przy przechwyceniu transmisji lub wycieku bazy.

Typowe pytanie: zaprojektuj bezpieczny mechanizm logowania — hashowanie hasła (nie szyfrowanie odwracalne!), transmisja przez HTTPS, ochrona przed CSRF przy formularzu logowania, limitowanie prób (ochrona przed brute-force), i zgodność z RODO co do przechowywanych danych użytkownika.
