Testowanie oprogramowania

1. Siedem zasad testowania oprogramowania

  1. Testowanie wykazuje obecność defektów, nie ich brak — testy mogą pokazać, że błędy istnieją, ale nigdy nie dowodzą, że oprogramowanie jest całkowicie wolne od błędów (brak wykrytych defektów ≠ brak defektów).
  2. Wyczerpujące testowanie jest niemożliwe — przetestowanie wszystkich możliwych kombinacji danych wejściowych i scenariuszy jest w praktyce nieosiągalne (poza trywialnie prostymi programami) — trzeba priorytetyzować (analiza ryzyka, techniki projektowania testów).
  3. Wczesne testowanie oszczędza czas i pieniądze — defekty wykryte na wczesnym etapie (np. w fazie wymagań/projektu) są znacznie tańsze w naprawie niż te wykryte po wdrożeniu produkcyjnym.
  4. Grupowanie defektów (defect clustering) — defekty nie rozkładają się równomiernie — zwykle niewielka liczba modułów/komponentów zawiera większość wykrytych błędów (zasada Pareto: ~80% błędów w ~20% modułów).
  5. Paradoks pestycydu (pesticide paradox) — powtarzanie tych samych testów wielokrotnie z czasem przestaje wykrywać nowe błędy (jak insekty uodparniające się na pestycyd) — testy trzeba regularnie przeglądać i uzupełniać nowymi przypadkami.
  6. Testowanie zależy od kontekstu — nie ma jednego uniwersalnego podejścia — testowanie systemu medycznego (krytyczne bezpieczeństwo) różni się od testowania prostej strony informacyjnej.
  7. Błąd nieobecności defektów (absence-of-errors fallacy) — znalezienie i naprawienie wszystkich zgłoszonych defektów nie gwarantuje sukcesu systemu — oprogramowanie może być technicznie bezbłędne, ale nie spełniać rzeczywistych potrzeb/oczekiwań użytkownika.
Te zasady (ISTQB) to fundament myślenia o testowaniu — częste pytanie egzaminacyjne to podanie konkretnego przykładu/scenariusza ilustrującego jedną z zasad (np. "paradoks pestycydu" przy zawsze tym samym zestawie testów regresyjnych — patrz punkt 4).

2. TDD (Test-Driven Development)

Technika programowania, w której test pisze się przed kodem produkcyjnym — kod implementacji powstaje jako odpowiedź na wymagania zakodowane w teście, nie odwrotnie.

Cykl Red-Green-Refactor (3 etapy)

  1. RED — napisz test, który nie przechodzi
    Napisz test dla funkcjonalności, która jeszcze nie istnieje (albo nie jest jeszcze zaimplementowana poprawnie) — test musi się nie powieść (bo kodu jeszcze nie ma), co potwierdza, że test faktycznie sprawdza coś realnego.
  2. GREEN — napisz minimalny kod, żeby test przeszedł
    Zaimplementuj tylko tyle kodu, żeby test przeszedł — bez przesadnej elegancji na tym etapie, celem jest szybkie osiągnięcie działającego (zielonego) stanu.
  3. REFACTOR — uporządkuj kod, zachowując zielone testy
    Popraw jakość/czytelność kodu (usuń duplikację, poprawi nazwy, wydziel funkcje) — testy napisane wcześniej działają jako "siatka bezpieczeństwa": jeśli refaktoryzacja coś zepsuje, testy to natychmiast wykryją.
RED → GREEN → REFACTOR → (powrót do RED dla kolejnej funkcjonalności) → ...

Korzyści TDD

  • kod od razu ma zestaw testów — nie trzeba dopisywać ich później "z pamięci"
  • projektowanie API "z perspektywy użycia" — pisząc test najpierw, naturalnie myślisz, jak wygodnie ma się z kodu korzystać
  • wysoka pewność przy refaktoryzacji — testy szybko wykrywają regresję (patrz punkt 4)
  • zapobiega pisaniu kodu "na wszelki wypadek" — implementujesz tylko to, co faktycznie wymagane przez test

Wady/wyzwania TDD

  • wymaga zmiany przyzwyczajeń — na początku wolniejsze niż "zwykłe" programowanie
  • źle napisane testy mogą "zakotwiczyć" niewłaściwy design (test zbyt ściśle powiązany z implementacją, utrudniający późniejsze zmiany)
  • nie zawsze łatwe do zastosowania przy złożonej logice UI/integracjach zewnętrznych
Typowe pytanie: zademonstruj cykl TDD na prostym przykładzie (np. implementacja funkcji sumującej dwie liczby) — pokaż kod testu w fazie RED, minimalną implementację w GREEN, i przykładową poprawkę w REFACTOR.

3. Testy jednostkowe

Definicja

Testy sprawdzające najmniejszą, izolowaną jednostkę kodu (zwykle jedną metodę/funkcję) — w oderwaniu od reszty systemu (baz danych, sieci, plików, innych klas — te zależności zwykle zastępuje się atrapami/mockami).

Struktura typowego testu jednostkowego — Arrange-Act-Assert (AAA)

@Test
public void sumaDwochLiczb_dajePoprawnyWynik() {
    // Arrange — przygotowanie danych
    Kalkulator kalk = new Kalkulator();

    // Act — wykonanie testowanej operacji
    int wynik = kalk.dodaj(2, 3);

    // Assert — sprawdzenie wyniku
    assertEquals(5, wynik);
}

Do czego służą testy jednostkowe

  • wczesne wykrywanie błędów — na poziomie pojedynczej funkcji, zanim błąd "rozleje się" po całym systemie (patrz zasada 3, punkt 1)
  • dokumentacja "żywa" — test pokazuje, jak dana funkcja/metoda ma się zachowywać, w formie wykonywalnego przykładu
  • bezpieczna refaktoryzacja — testy jednostkowe jako "siatka bezpieczeństwa" przy zmianach kodu (patrz TDD, punkt 2)
  • szybka informacja zwrotna — testy jednostkowe są zwykle bardzo szybkie (milisekundy), można je uruchamiać setki razy dziennie

Cechy dobrego testu jednostkowego — zasada F.I.R.S.T.

CechaZnaczenie
Fast (szybki)wykonuje się bardzo szybko — brak połączeń z bazą/siecią
Independent (niezależny)nie zależy od innych testów, ani od kolejności wykonania
Repeatable (powtarzalny)ten sam wynik przy każdym uruchomieniu, niezależnie od środowiska
Self-validating (samosprawdzający)test sam jednoznacznie stwierdza sukces/porażkę (bez ręcznej interpretacji wyniku)
Timely (na czas)pisany w odpowiednim momencie — najlepiej przed/razem z kodem (patrz TDD)

Mocki, stuby, fake'i (test doubles)

Zastępniki prawdziwych zależności, umożliwiające izolację testowanej jednostki: stub — zwraca z góry ustalone dane; mock — dodatkowo weryfikuje, czy dana metoda została faktycznie wywołana (i z jakimi argumentami); fake — uproszczona, działająca implementacja (np. baza danych w pamięci zamiast rzeczywistej).

Typowe pytanie: napisz test jednostkowy dla podanej metody/funkcji, z użyciem struktury AAA, i wskaż, jaką zależność (jeśli jakąś) należałoby zastąpić mockiem, żeby test był izolowany.

4. Testy regresyjne

Definicja

Testy sprawdzające, czy wcześniej działająca funkcjonalność wciąż działa poprawnie po wprowadzeniu zmian w kodzie (nowa funkcja, poprawka błędu, refaktoryzacja) — celem jest wykrycie regresji: sytuacji, gdy zmiana w jednym miejscu przypadkowo "zepsuła" coś innego, co wcześniej działało.

Dlaczego regresja się zdarza

W złożonym systemie różne fragmenty kodu są ze sobą powiązane (współdzielone funkcje, zmienne, zależności między modułami) — zmiana w jednym miejscu może mieć nieoczekiwany, "efekt motyla" wpływ na zupełnie inną część systemu, o której programista mógł nawet nie myśleć podczas wprowadzania zmiany.

Przykłady zastosowania testów regresyjnych

  • przed każdym wydaniem (release) — pełny zestaw testów regresyjnych uruchamiany, żeby upewnić się, że nowa wersja nie zepsuła istniejących funkcji
  • po naprawie błędu (bug fix) — test odtwarzający konkretny, wcześniej zgłoszony błąd, dodany do zestawu regresyjnego — zapobiega ponownemu wystąpieniu tego samego błędu w przyszłości ("bug nigdy nie powinien wrócić bez wykrycia")
  • w pipeline CI/CD (patrz przedmiot Technologie DevOps) — automatyczne uruchomienie testów regresyjnych przy każdym pull request/push do głównego brancha, zanim zmiana zostanie scalona
  • po aktualizacji zależności/biblioteki — sprawdzenie, czy nowa wersja zewnętrznej biblioteki nie wprowadziła niekompatybilnych zmian wpływających na istniejącą funkcjonalność

Automatyzacja testów regresyjnych

Ze względu na powtarzalność (te same testy uruchamiane wielokrotnie przy każdej zmianie), testy regresyjne są klasycznym kandydatem do automatyzacji — ręczne powtarzanie tysięcy przypadków testowych przy każdym wydaniu byłoby niepraktyczne czasowo.

Powiązanie z paradoksem pestycydu (punkt 1)

Sam zestaw testów regresyjnych musi być regularnie rozszerzany — jeśli zawsze uruchamia się identyczny, niezmieniany zestaw testów, z czasem przestaje on wykrywać nowe typy błędów (paradoks pestycydu) — nowe funkcjonalności i naprawione błędy powinny dodawać nowe przypadki do zestawu regresyjnego.

Testy regresyjne vs testy jednostkowe

Testy jednostkoweTesty regresyjne
Celweryfikacja poprawności nowej/aktualnej jednostki koduweryfikacja, że stara funkcjonalność wciąż działa po zmianach
Zakreszwykle mały (jedna metoda/klasa)może obejmować cały system (testy jednostkowe, integracyjne, end-to-end razem)
Relacjatesty jednostkowe (i inne) składają się na zestaw regresyjny — "regresja" to sposób użycia testów, nie osobny typ testu z inną strukturą

5. Automatyzacja testów aplikacji webowych (Selenium)

Selenium — idea

Framework do automatyzacji interakcji z przeglądarką — symuluje działania użytkownika (kliknięcia, wpisywanie tekstu, nawigację) programowo, pozwalając automatycznie testować aplikacje webowe "tak, jak robiłby to człowiek".

WebDriver — komponent centralny

API pozwalające programowo kontrolować przeglądarkę (Chrome, Firefox, Edge) — każda przeglądarka wymaga odpowiedniego sterownika (np. ChromeDriver dla Chrome), tłumaczącego komendy Selenium na rzeczywiste akcje w przeglądarce.

Przykład — test w Java (JUnit + Selenium)

WebDriver driver = new ChromeDriver();
driver.get("https://example.com/logowanie");

WebElement pole_login = driver.findElement(By.id("login"));
WebElement pole_haslo = driver.findElement(By.id("haslo"));
WebElement przycisk = driver.findElement(By.id("zaloguj"));

pole_login.sendKeys("jan");
pole_haslo.sendKeys("tajnehaslo");
przycisk.click();

WebElement komunikat = driver.findElement(By.className("witaj"));
assertEquals("Witaj, jan!", komunikat.getText());

driver.quit();

Przykład — test w C# (NUnit + Selenium)

IWebDriver driver = new ChromeDriver();
driver.Navigate().GoToUrl("https://example.com/logowanie");

driver.FindElement(By.Id("login")).SendKeys("jan");
driver.FindElement(By.Id("haslo")).SendKeys("tajnehaslo");
driver.FindElement(By.Id("zaloguj")).Click();

var komunikat = driver.FindElement(By.ClassName("witaj"));
Assert.AreEqual("Witaj, jan!", komunikat.Text);

driver.Quit();

Oczekiwanie na elementy (waits)

Strony webowe (zwłaszcza z JavaScriptem) renderują się asynchronicznie — element może jeszcze nie istnieć w DOM w momencie, gdy test próbuje go znaleźć:

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement element = wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("wynik")));
Klasyczny błąd: brak odpowiedniego oczekiwania prowadzi do "kruchych" (flaky) testów, które losowo się nie powodzą, zależnie od szybkości ładowania strony — jawne oczekiwanie (explicit wait) na konkretny warunek jest bardziej niezawodne niż stałe sleep().

Wzorzec Page Object

Technika organizacji kodu testów — dla każdej strony/widoku aplikacji tworzy się osobną klasę ("Page Object") skupiającą lokalizatory elementów i akcje na tej stronie:

class StronaLogowania {
    private WebDriver driver;
    private By pole_login = By.id("login");
    private By przycisk = By.id("zaloguj");

    public void zaloguj(String login, String haslo) {
        driver.findElement(pole_login).sendKeys(login);
        driver.findElement(By.id("haslo")).sendKeys(haslo);
        driver.findElement(przycisk).click();
    }
}

Zaleta: jeśli struktura strony się zmieni (np. zmiana id pola), poprawka jest potrzebna tylko w jednym miejscu (klasie Page Object), nie w każdym teście korzystającym z tej strony.

Typowy proces tworzenia testów automatycznych

  1. zidentyfikuj kluczowe scenariusze użytkownika do automatyzacji (zwykle najpierw "happy path" — typowa, poprawna ścieżka)
  2. skonfiguruj środowisko (WebDriver, sterownik przeglądarki, framework testowy — JUnit/NUnit/TestNG)
  3. zaimplementuj Page Objects dla stron uczestniczących w scenariuszu
  4. napisz test korzystający z Page Objects, z jasną strukturą AAA (patrz punkt 3) i odpowiednimi asercjami
  5. dodaj jawne oczekiwania (waits) tam, gdzie strona ładuje się asynchronicznie
  6. zintegruj z pipeline CI/CD (patrz przedmiot Technologie DevOps), żeby testy uruchamiały się automatycznie przy każdej zmianie kodu
Testy Selenium to typowo testy end-to-end (najwyższy poziom "piramidy testów") — wolniejsze i bardziej kosztowne w utrzymaniu niż testy jednostkowe, ale sprawdzają system "z perspektywy użytkownika", przez rzeczywistą przeglądarkę, wykrywając problemy niewidoczne na niższych poziomach (np. błędy w integracji frontend-backend, problemy z layoutem).

7. Pokrycie kodu (code coverage)

Metryka mówiąca, jaki procent kodu produkcyjnego jest wykonywany podczas przebiegu zestawu testów — narzędzie pomocnicze do oceny, jak dokładnie testy "sprawdzają" kod, ale nie jest samo w sobie miarą jakości testów.

Rodzaje pokrycia (od najsłabszego do najsilniejszego)

TypCo mierzy
Pokrycie instrukcji (statement coverage) jaki % linii/instrukcji kodu został wykonany przynajmniej raz
Pokrycie decyzji/rozgałęzień (branch/decision coverage) czy każda możliwa gałąź warunku (if/else, każdy wynik pętli) została wykonana — silniejsze niż pokrycie instrukcji, bo if (a && b) może mieć 100% pokrycia instrukcji, ale nie sprawdzić obu gałęzi warunku
Pokrycie warunków (condition coverage) czy każdy pojedynczy warunek logiczny (w złożonym wyrażeniu z &&/||) przyjął zarówno wartość true, jak i false
Pokrycie ścieżek (path coverage) czy wszystkie możliwe kombinacje ścieżek przez kod zostały przetestowane — najsilniejsze, ale liczba ścieżek rośnie wykładniczo z liczbą warunków (podobnie do problemu z wyczerpującym testowaniem, patrz zasada 2, punkt 1)

Przykład — dlaczego 100% pokrycia instrukcji nie wystarcza

if (a > 0 && b > 0) {
    wynik = a / b;   // instrukcja wykonana
}

Jeden test z a=5, b=2 daje 100% pokrycia instrukcji (linia się wykonała) — ale nie sprawdza żadnej z gałęzi, gdzie warunek jest fałszywy, ani zachowania przy b=0 (mimo że warunek to wyklucza, błąd logiczny w samym warunku by przeszedł niezauważony).

Ograniczenia pokrycia kodu jako metryki

Wysokie pokrycie kodu nie gwarantuje braku błędów — test może "przejść przez" linię kodu bez sprawdzenia (asercji), czy wynik jest poprawny. Klasyczny przykład: test wywołujący funkcję, ale bez żadnego assert na wyniku, "pokrywa" kod (zwiększa metrykę), ale nie weryfikuje niczego — pokrycie mierzy wykonanie kodu, nie jego poprawność.

Praktyczne zastosowanie

Pokrycie kodu używa się głównie do identyfikacji obszarów bez testów (np. "ten moduł ma 20% pokrycia — prawdopodobnie warto dodać tam testy"), a nie jako sztywny cel liczbowy do "wyciskania" (100% pokrycia zwykle nie jest praktycznym/opłacalnym celem — pewne fragmenty kodu, np. proste gettery/settery, rzadko wymagają dedykowanych testów).

Typowe pytanie: dla podanego fragmentu kodu z warunkiem złożonym, wskaż minimalny zestaw danych testowych potrzebny do osiągnięcia pełnego pokrycia decyzji (branch coverage), i wyjaśnij, czym różniłby się on od zestawu wystarczającego tylko do pokrycia instrukcji.
