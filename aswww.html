Administracja serwerami WWW

1. HTTP, HTTPS, TLS, handshake TLS

(podstawy HTTP — patrz przedmiot Sieci komputerowe/Języki hipertekstowe; tu głębsze omówienie TLS)

HTTP — przypomnienie

Protokół żądanie-odpowiedź, bezstanowy, domyślny port 80. Metody GET/POST/PUT/DELETE, kody statusu 2xx/3xx/4xx/5xx.

HTTPS = HTTP + TLS

HTTPS to HTTP przesyłane przez szyfrowany kanał TLS (Transport Layer Security, następca SSL) — domyślny port 443. Zapewnia trzy własności bezpieczeństwa:

  • poufność (confidentiality) — dane szyfrowane, niezrozumiałe dla podsłuchującego po drodze
  • integralność (integrity) — wykrycie, czy dane zostały zmodyfikowane w transmisji
  • autentyczność (authentication) — potwierdzenie, że łączymy się z prawdziwym, oczekiwanym serwerem (przez certyfikat), nie z podszywającym się atakującym

Certyfikat X.509

Elektroniczny dokument potwierdzający tożsamość serwera — zawiera nazwę domeny, klucz publiczny serwera, okres ważności, i podpis zaufanej instytucji certyfikującej (CA — Certificate Authority). Przeglądarka ufa certyfikatowi, jeśli CA, która go podpisała, jest w jej wbudowanej liście zaufanych CA (łańcuch zaufania — chain of trust).

Handshake TLS 1.2 (klasyczny, pełny przebieg)

  1. ClientHello — klient wysyła obsługiwane wersje TLS, listę szyfrów (cipher suites), losową wartość
  2. ServerHello — serwer wybiera wersję/szyfr, wysyła swój certyfikat (z kluczem publicznym) i swoją losową wartość
  3. weryfikacja certyfikatu — klient sprawdza podpis CA, ważność, zgodność nazwy domeny
  4. wymiana kluczy — klient generuje tajny materiał (pre-master secret), szyfruje go kluczem publicznym serwera (kryptografia asymetryczna) i wysyła; obie strony na tej podstawie (+ obie losowe wartości) wyliczają identyczny klucz sesyjny
  5. Finished — obie strony potwierdzają zakończenie handshake'u (zaszyfrowaną wiadomością testową)
  6. dalsza komunikacja szyfrowana symetrycznie uzgodnionym kluczem sesyjnym (szybsze niż szyfrowanie asymetryczne dla dużych ilości danych)

TLS 1.3 — uproszczenie i skrócenie

TLS 1.3 redukuje handshake do jednej rundy wymiany (1-RTT) zamiast dwóch w TLS 1.2 — szybsze nawiązanie połączenia; usuwa też przestarzałe, słabsze algorytmy kryptograficzne dostępne jeszcze w 1.2.

Kryptografia symetryczna vs asymetryczna w TLS (przypomnienie)

SNI (Server Name Indication)

Rozszerzenie TLS pozwalające klientowi już w ClientHello podać nazwę domeny, do której się łączy — niezbędne, żeby jeden serwer (adres IP) mógł hostować wiele różnych domen z różnymi certyfikatami (bez SNI, serwer nie wiedziałby, którego certyfikatu użyć, zanim jeszcze poznałby żądaną domenę).

Typowe pytanie: opisz krok po kroku pełny handshake TLS 1.2, wskazując, w którym momencie używana jest kryptografia asymetryczna, a w którym symetryczna, i wyjaśnij rolę certyfikatu X.509 w budowaniu zaufania.

2. Zadania klienta i serwera WWW

Zadania klienta (przeglądarki)

  • rozwiązanie nazwy domeny — zapytanie DNS o adres IP serwera (patrz przedmiot Sieci komputerowe)
  • nawiązanie połączenia — TCP handshake, potencjalnie TLS handshake (patrz punkt 1)
  • wysłanie żądania HTTP — metoda, ścieżka, nagłówki (np. User-Agent, Accept, Cookie)
  • odebranie i interpretacja odpowiedzi — parsowanie HTML/CSS/JS, budowa DOM (patrz przedmiot Języki hipertekstowe), renderowanie strony
  • zarządzanie cache — przechowywanie zasobów lokalnie wg nagłówków (Cache-Control, ETag), by nie pobierać ich ponownie bez potrzeby
  • obsługa cookies/sesji — przechowywanie i odsyłanie identyfikatorów sesji

Zadania serwera WWW

  • nasłuchiwanie połączeń na skonfigurowanych portach (80/443)
  • parsowanie żądania HTTP — metoda, ścieżka, nagłówki, ewentualne ciało żądania
  • routing żądania — decyzja, jak obsłużyć dane URL: plik statyczny, przekazanie do backendu aplikacyjnego, przekierowanie, błąd 404
  • obsługa treści statycznej — bezpośrednie wysłanie plików HTML/CSS/JS/obrazów z dysku
  • delegacja do backendu — dla treści dynamicznej, przekazanie żądania do aplikacji (PHP-FPM, serwer aplikacyjny Java, proces Node.js itd. — patrz punkt 3, reverse proxy)
  • zarządzanie połączeniami — obsługa wielu klientów jednocześnie (procesy/wątki/event loop, zależnie od architektury serwera)
  • logowanie — zapisywanie informacji o żądaniach (adres IP, czas, kod odpowiedzi) do logów dostępu
  • bezpieczeństwo — TLS termination (patrz punkt 1), nagłówki bezpieczeństwa, ograniczenia dostępu

Architektury obsługi wielu połączeń przez serwer

ModelZasadaPrzykład
Proces/wątek na połączeniekażde połączenie obsługiwane w osobnym procesie/wątkuklasyczny Apache (mod_prefork/mod_worker)
Event loop (asynchroniczny)jeden (lub kilka) wątek obsługuje wiele połączeń naraz, przełączając się między nimi bez blokowania na I/ONginx, Node.js

Model event loop zwykle skaluje się lepiej przy dużej liczbie równoczesnych połączeń (mniejszy narzut pamięciowy niż jeden proces/wątek na połączenie), stąd popularność Nginx jako serwera front-endowego dla dużego ruchu.

Typowe pytanie: opisz pełną sekwencję zdarzeń od wpisania adresu URL do wyświetlenia strony, uwzględniając zadania klienta i serwera w każdym kroku (DNS, TCP/TLS handshake, żądanie/odpowiedź HTTP, renderowanie).

3. Konfiguracja hostów WWW i serwerów Proxy

Wirtualne hosty (virtual hosts)

Mechanizm hostowania wielu niezależnych witryn/domen na jednym fizycznym serwerze (jednym adresie IP) — serwer rozróżnia, o którą witrynę chodzi, na podstawie nagłówka Host żądania HTTP (i SNI dla HTTPS, patrz punkt 1).

Konfiguracja Apache — VirtualHost

<VirtualHost *:80>
    ServerName example.com
    DocumentRoot /var/www/example.com
    ErrorLog /var/log/apache2/example.com-error.log
</VirtualHost>

<VirtualHost *:80>
    ServerName drugastrona.pl
    DocumentRoot /var/www/drugastrona.pl
</VirtualHost>

Konfiguracja Nginx — server block

server {
    listen 80;
    server_name example.com;
    root /var/www/example.com;

    location / {
        try_files $uri $uri/ =404;
    }
}

Reverse proxy — zasada działania

Serwer pośredniczący, który przyjmuje żądania od klientów i przekazuje je do jednego lub wielu serwerów "za sobą" (backendów) — z perspektywy klienta widoczny jest tylko reverse proxy, nie rzeczywiste serwery aplikacyjne.

Klient → Reverse Proxy (np. Nginx) → Backend (np. aplikacja Node.js/Java/Python na porcie 8080)

Konfiguracja reverse proxy w Nginx

server {
    listen 80;
    server_name aplikacja.example.com;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

proxy_set_header X-Real-IP — backend "za" proxy widziałby normalnie adres IP proxy jako źródło żądania; ten nagłówek przekazuje prawdziwy adres klienta do backendu.

Zastosowania reverse proxy

ZastosowanieOpis

Serwowanie treści statycznejproxy (np. Nginx) obsługuje pliki statyczne bezpośrednio, przekazując do backendu tylko żądania wymagające logiki aplikacji — odciąża wolniejszy backend

4. HTTP/2 i HTTP/3

Problem HTTP/1.1 — head-of-line blocking

W HTTP/1.1 każde żądanie w ramach jednego połączenia TCP musi zaczekać na zakończenie poprzedniego (albo przeglądarka otwiera wiele osobnych połączeń równolegle, co ma swój narzut) — powolne pobranie jednego zasobu blokuje kolejkę pozostałych.

HTTP/2 — multipleksowanie

CechaOpis
Multipleksowaniewiele żądań/odpowiedzi przesyłanych równolegle przez jedno połączenie TCP, w niezależnych "strumieniach" (streams) — koniec head-of-line blocking na poziomie HTTP
Kompresja nagłówków (HPACK)nagłówki HTTP (często powtarzalne między żądaniami) kompresowane, redukując narzut przesyłu
Server pushserwer może "z góry" wysłać zasoby, o które klient jeszcze nie poprosił, ale prawdopodobnie będzie potrzebował (np. CSS/JS przy pierwszym żądaniu HTML) — w praktyce rzadko używane, częściowo wycofywane
Binarny formatramki binarne zamiast czystego tekstu (jak w HTTP/1.1) — bardziej efektywne parsowanie

HTTP/2 nadal działa na TCP — dziedziczy więc pewne ograniczenia TCP (np. head-of-line blocking na poziomie samego TCP, gdy zgubi się pakiet — wszystkie strumienie czekają na retransmisję, nawet jeśli dotyczyła tylko jednego z nich).

HTTP/3 — oparty na QUIC (UDP)

Zamiast TCP, HTTP/3 działa na protokole QUIC, zbudowanym na UDP (patrz przedmiot Sieci komputerowe) — rozwiązuje head-of-line blocking na poziomie transportowym, bo utrata jednego pakietu wpływa tylko na jeden strumień, nie na wszystkie.

Zaleta QUIC/HTTP3Wyjaśnienie
Szybsze nawiązanie połączeniaQUIC integruje uzgodnienie transportu i szyfrowania (TLS 1.3) w jednym uzgodnieniu — mniej rund komunikacji niż TCP+TLS osobno
Migracja połączeniapołączenie może "przetrwać" zmianę adresu IP klienta (np. przełączenie Wi-Fi → dane mobilne) bez zrywania sesji
Wbudowane szyfrowanieQUIC jest zawsze szyfrowany (TLS 1.3 wbudowany), nie istnieje "QUIC bez TLS"

5. Nagłówki bezpieczeństwa HTTP

Nagłówki odpowiedzi HTTP konfigurowane po stronie serwera, instruujące przeglądarkę, jak bezpiecznie traktować odebraną treść — jeden z podstawowych, praktycznych elementów utwardzania (hardening) serwera WWW.

HSTS (HTTP Strict Transport Security)

Strict-Transport-Security: max-age=31536000; includeSubDomains

Instruuje przeglądarkę, żeby przez podany czas (w sekundach) zawsze łączyła się z domeną przez HTTPS, nawet jeśli użytkownik wpisze http:// — chroni przed atakiem "downgrade" (zmuszenie ofiary do połączenia przez niezaszyfrowane HTTP, gdzie łatwiej podsłuchać/zmodyfikować ruch).

CSP (Content Security Policy)

Content-Security-Policy: default-src 'self'; script-src 'self' cdn.example.com

Ogranicza, z jakich źródeł strona może wczytywać skrypty/style/obrazy itd. — kluczowa ochrona przed XSS (patrz przedmiot Projektowanie aplikacji internetowych): nawet jeśli atakującemu uda się wstrzyknąć złośliwy <script>, przeglądarka odmówi jego wykonania, jeśli nie pochodzi z dozwolonego źródła.

X-Frame-Options

X-Frame-Options: DENY

Zabrania (albo ogranicza) osadzania strony w <iframe> na innej witrynie — chroni przed clickjackingiem (nakłonienie użytkownika do kliknięcia czegoś innego, niż mu się wydaje, przez przezroczystą ramkę nałożoną na inną stronę).

Inne istotne nagłówki

NagłówekZastosowanie
X-Content-Type-Options: nosniffzabrania przeglądarce "zgadywania" typu MIME innego niż zadeklarowany — zapobiega niektórym atakom opartym na błędnej interpretacji treści
Referrer-Policykontroluje, ile informacji o adresie poprzedniej strony (referrer) jest wysyłane przy przechodzeniu na inną domenę — ochrona prywatności
Set-Cookie: ...; Secure; HttpOnly; SameSite=StrictSecure — cookie wysyłane tylko przez HTTPS; HttpOnly — niedostępne dla JavaScript (ochrona przed XSS wykradającym cookie sesji); SameSite — ograniczenie wysyłania cookie przy żądaniach z innych domen (ochrona przed CSRF, patrz przedmiot Projektowanie aplikacji internetowych)

Konfiguracja w Nginx

server {
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Frame-Options "DENY" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Content-Security-Policy "default-src 'self'" always;
}
Typowe pytanie: dla opisanej podatności (np. "strona podatna na osadzenie w iframe innej witryny" albo "wstrzykiwanie złośliwych skryptów") wskaż odpowiedni nagłówek bezpieczeństwa jako część rozwiązania i wyjaśnij mechanizm jego działania.
