Wzorce projektowe

1. Pojęcie wzorca projektowego — Alexander i "Banda Czterech"

Christopher Alexander — pierwotna idea (architektura budynków)

Pojęcie wzorca zostało zapożyczone z architektury (budynków, nie oprogramowania!). Alexander opisywał wzorzec jako sprawdzony, powtarzalny sposób rozwiązania określonego problemu, występującego wielokrotnie w określonym kontekście (środowisku) — tak, że można go zastosować wielokrotnie, dostosowując do konkretnej sytuacji, bez rozwiązywania problemu "od zera" za każdym razem.

Zauważył, że dobre rozwiązania architektoniczne (np. "okno z widokiem na ogród", "wejście na poziomie ulicy") powtarzają się w wielu dobrze zaprojektowanych budynkach — nazwał i skatalogował takie powtarzalne rozwiązania jako wzorce, w swojej książce "A Pattern Language".

"Banda Czterech" (Gang of Four) — przeniesienie do programowania

Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides — autorzy książki "Design Patterns: Elements of Reusable Object-Oriented Software" (1994), która przeniosła ideę Alexandra na programowanie obiektowe.

Definicja GoF: wzorzec projektowy to ogólne, nazwane rozwiązanie powszechnie występującego problemu projektowego w programowaniu obiektowym — opisane niezależnie od konkretnego języka/implementacji, gotowe do wielokrotnego zastosowania w różnych projektach.

Struktura opisu wzorca (wg GoF)

ElementOpis
Nazwakrótka, powszechnie rozpoznawalna etykieta ułatwiająca komunikację między programistami ("użyj tu Observera" mówi więcej niż długi opis słowny)
Problemkiedy stosować wzorzec — jaki problem/sytuacja go wymaga, jakie są objawy "braku" tego wzorca w kodzie
Rozwiązanieopis elementów projektu (klasy, relacje) rozwiązujących problem, w formie ogólnej (szablonu), nie konkretnego kodu
Konsekwencjekompromisy — co wzorzec zyskuje, a co kosztuje (np. elastyczność vs dodatkowa złożoność, więcej klas)

Klasyfikacja wzorców GoF

23 klasyczne wzorce podzielone na trzy kategorie wg celu:

KategoriaCel
Kreacyjne (creational)sposoby tworzenia obiektów, ukrywające logikę tworzenia i zwiększające elastyczność (punkt 3)
Strukturalne (structural)sposoby komponowania klas/obiektów w większe struktury (punkt 4)
Behawioralne (behavioral)sposoby komunikacji i przydziału odpowiedzialności między obiektami (punkt 2)
Kluczowa różnica podejść: Alexander opisywał wzorce dla fizycznych struktur (budynki, przestrzenie), GoF przeniosło samą ideę (nazwany, powtarzalny szablon rozwiązania problemu w kontekście) na świat abstrakcyjnych struktur kodu obiektowego — sam sposób myślenia o "katalogowaniu sprawdzonych rozwiązań" pozostał ten sam.

2. Wzorce behawioralne

Chain of Responsibility (łańcuch zobowiązań)

Przekazuje żądanie po łańcuchu potencjalnych obsługujących, aż jeden z nich je obsłuży — nadawca żądania nie musi znać, który konkretnie obiekt w łańcuchu je obsłuży, co odsprzęga nadawcę od konkretnych odbiorców.

abstract class Handler {
    protected Handler nastepny;
    void ustawNastepny(Handler h) { nastepny = h; }
    abstract void obsluz(Zadanie z);
}
class HandlerA extends Handler {
    void obsluz(Zadanie z) {
        if (pasuje(z)) { /* obsłuż */ }
        else if (nastepny != null) nastepny.obsluz(z);
    }
}

Zastosowanie: middleware/filtry HTTP (patrz przedmiot Programowanie aplikacji internetowych), obsługa zdarzeń UI propagowana od dziecka do rodzica, systemy autoryzacji sprawdzające kolejne poziomy uprawnień.

Command (polecenie)

Zamienia żądanie/akcję w samodzielny obiekt, hermetyzujący wszystkie informacje potrzebne do jej wykonania — pozwala parametryzować obiekty akcjami, kolejkować je, logować i wycofywać (undo).

interface Command { void wykonaj(); void cofnij(); }

class DodajTekstCommand implements Command {
    Dokument doc; String tekst;
    void wykonaj() { doc.dodaj(tekst); }
    void cofnij() { doc.usun(tekst); }
}

Zastosowanie: mechanizmy undo/redo w edytorach, kolejki zadań, makra nagrywające sekwencję akcji, przyciski/menu w GUI (każdy powiązany z obiektem Command).

Interpreter

Definiuje reprezentację gramatyki prostego języka i interpreter zdań tego języka — każda reguła gramatyki odpowiada klasie, drzewo obiektów reprezentuje konkretne zdanie do zinterpretowania.

interface Wyrazenie { int interpretuj(); }
class Liczba implements Wyrazenie {
    int wartosc;
    int interpretuj() { return wartosc; }
}
class Dodawanie implements Wyrazenie {
    Wyrazenie lewy, prawy;
    int interpretuj() { return lewy.interpretuj() + prawy.interpretuj(); }
}

Zastosowanie: parsery prostych wyrażeń matematycznych/logicznych, silniki reguł biznesowych, języki konfiguracyjne — rzadko stosowany "wprost" dziś (zastępowany gotowymi bibliotekami parserów), ale ważny koncepcyjnie.

Iterator

Zapewnia jednolity sposób sekwencyjnego przechodzenia po elementach kolekcji, bez ujawniania jej wewnętrznej reprezentacji (tablica, lista, drzewo) — patrz przedmiot Programowanie obiektowe 2, protokół __iter__/__next__ w Pythonie, czy Iterator w Javie.

Iterator<Integer> it = lista.iterator();
while (it.hasNext()) {
    int x = it.next();
}

Zastosowanie: wszystkie kolekcje standardowych bibliotek (List, Set, Map), pętle for-each, generatory (patrz przedmiot Języki skryptowe).

Mediator (mediator)

Centralizuje komunikację między grupą obiektów w jednym obiekcie-pośredniku — obiekty nie odwołują się bezpośrednio do siebie nawzajem (co dałoby "gęstą siatkę" zależności), tylko przez mediatora, co redukuje liczbę wzajemnych powiązań.

class DialogMediator {
    Checkbox chk; Button btn;
    void powiadom(Object nadawca, String zdarzenie) {
        if (nadawca == chk && zdarzenie.equals("zmiana")) {
            btn.setEnabled(chk.isChecked());
        }
    }
}

Zastosowanie: koordynacja komponentów formularza GUI (włączanie/wyłączanie pól zależnie od innych), kontroler ruchu lotniczego jako klasyczna analogia, chat room łączący uczestników.

Memento

Pozwala zapisać i później przywrócić wewnętrzny stan obiektu, bez naruszania jego enkapsulacji (zewnętrzny kod nie widzi szczegółów tego stanu) — podstawa mechanizmów undo/redo, obok wzorca Command.

class Memento { private String stan; Memento(String s) { stan = s; } String getStan() { return stan; } }

class Edytor {
    String tresc;
    Memento zapisz() { return new Memento(tresc); }
    void przywroc(Memento m) { tresc = m.getStan(); }
}

Zastosowanie: historia zmian w edytorach tekstu/grafiki, punkty zapisu w grach (save states), transakcje z możliwością wycofania (rollback).

Observer (obserwator)

Definiuje zależność jeden-do-wielu między obiektami — gdy stan jednego obiektu (subjekt/podmiot) się zmienia, wszyscy zarejestrowani obserwatorzy są automatycznie powiadamiani i mogą zaktualizować się w odpowiedzi.

interface Observer { void aktualizuj(String dane); }

class Subjekt {
    List<Observer> obserwatorzy = new ArrayList<>();
    void dodajObserwatora(Observer o) { obserwatorzy.add(o); }
    void powiadom(String dane) {
        for (Observer o : obserwatorzy) o.aktualizuj(dane);
    }
}

Zastosowanie: obsługa zdarzeń GUI, mechanizm publish-subscribe (patrz RabbitMQ, przedmiot Programowanie sieciowe), reaktywne frameworki UI (React, Vue), Observer to podstawa wielu architektur event-driven.

State (stan)

Obiekt zmienia swoje zachowanie w zależności od wewnętrznego stanu, tak jakby zmieniał klasę — logika każdego stanu wydzielona do osobnej klasy implementującej wspólny interfejs, zamiast rozbudowanej instrukcji if/switch na polu-fladze stanu.

interface Stan { void obsluz(Zamowienie z); }
class StanNowe implements Stan {
    void obsluz(Zamowienie z) { z.ustawStan(new StanWyslane()); }
}

Zastosowanie: maszyny stanów (np. stan zamówienia: nowe → opłacone → wysłane → dostarczone), gry (stan gracza: bieganie/skakanie/atakowanie), protokoły sieciowe z formalnymi stanami.

Strategy (strategia)

Definiuje rodzinę wymiennych algorytmów rozwiązujących ten sam problem, kapsułkuje każdy w osobną klasę o wspólnym interfejsie i pozwala wybierać/podmieniać algorytm w czasie działania, bez zmiany kodu korzystającego z niego.

interface StrategiaSortowania { void sortuj(int[] tab); }
class QuickSort implements StrategiaSortowania { void sortuj(int[] tab) { /*...*/ } }
class MergeSort implements StrategiaSortowania { void sortuj(int[] tab) { /*...*/ } }

class Sorter {
    StrategiaSortowania strategia;
    void wykonaj(int[] tab) { strategia.sortuj(tab); }
}

Zastosowanie: różne algorytmy sortowania/wyszukiwania wymienne w locie, różne strategie walidacji, różne metody płatności w sklepie internetowym, funkcja porównująca przekazywana do sort().

Template Method (metoda szablonowa)

Definiuje ogólny "szkielet" algorytmu w metodzie klasy bazowej (z ustaloną kolejnością kroków), pozwalając podklasom nadpisać tylko poszczególne kroki, bez zmiany całej struktury algorytmu.

abstract class ProcesGotowania {
    final void gotuj() {           // metoda szablonowa — "final", struktura niezmienna
        przygotujSkladniki();
        gotujGlownaCzesc();
        podaj();
    }
    abstract void gotujGlownaCzesc();   // krok do nadpisania przez podklasy
    void przygotujSkladniki() { /* domyślna implementacja */ }
    void podaj() { /* domyślna implementacja */ }
}

Zastosowanie: frameworki definiujące ogólny cykl życia (np. cykl życia serwletu — patrz przedmiot Programowanie aplikacji internetowych), algorytmy różniące się tylko jednym krokiem (np. różne formaty eksportu danych z tym samym procesem walidacji).

Visitor (odwiedzający)

Pozwala dodać nową operację do całej hierarchii klas bez modyfikowania tych klas — operacja "odwiedza" strukturę obiektów z zewnątrz, dzięki mechanizmowi podwójnej dyspozycji (double dispatch).

interface Visitor { void odwiedz(Kolo k); void odwiedz(Kwadrat k); }
interface Figura { void akceptuj(Visitor v); }
class Kolo implements Figura {
    void akceptuj(Visitor v) { v.odwiedz(this); }
}
class ObliczPoleVisitor implements Visitor {
    void odwiedz(Kolo k) { /* oblicz pole koła */ }
    void odwiedz(Kwadrat k) { /* oblicz pole kwadratu */ }
}

Zastosowanie: operacje na drzewach składni (AST) w kompilatorach, eksport tej samej struktury danych do wielu formatów (XML, JSON, PDF) bez "zaśmiecania" klas modelu logiką eksportu.

Wspólny mianownik wzorców behawioralnych: skupiają się na tym, jak obiekty współpracują i komunikują się, oraz jak rozdzielona jest odpowiedzialność za konkretne zachowanie — w odróżnieniu od tworzenia obiektów (kreacyjne) czy ich strukturalnej kompozycji (strukturalne).

3. Wzorce kreacyjne

Abstract Factory (fabryka abstrakcyjna)

Zapewnia interfejs do tworzenia całych rodzin powiązanych/zależnych obiektów, bez określania ich konkretnych klas — klient korzysta wyłącznie z abstrakcyjnego interfejsu fabryki i produktów, niezależnie od tego, która konkretna "rodzina" jest aktualnie używana.

interface GUIFactory {
    Button tworzButton();
    Checkbox tworzCheckbox();
}
class WindowsFactory implements GUIFactory {
    Button tworzButton() { return new WindowsButton(); }
    Checkbox tworzCheckbox() { return new WindowsCheckbox(); }
}
class MacFactory implements GUIFactory {
    Button tworzButton() { return new MacButton(); }
    Checkbox tworzCheckbox() { return new MacCheckbox(); }
}

Zastosowanie: zestawy komponentów UI zgodne z jednym stylem/systemem (Windows/macOS), sterowniki baz danych zgodne z jednym dostawcą (różne, ale spójne implementacje Connection/Statement).

Builder (budowniczy)

Oddziela konstrukcję złożonego obiektu (z wieloma opcjonalnymi/wymaganymi polami) od jego finalnej reprezentacji — pozwala budować obiekt krok po kroku, z czytelnym, "płynnym" API, zamiast konstruktora z dziesiątkami parametrów.

Pizza p = new Pizza.Builder()
    .rozmiar("duża")
    .dodajSkladnik("ser")
    .dodajSkladnik("pieczarki")
    .build();

Zastosowanie: obiekty z wieloma opcjonalnymi parametrami (konfiguracje, zapytania SQL budowane programowo — Query Builder), obiekty niemutowalne wymagające wielu kroków inicjalizacji przed finalnym utworzeniem.

Factory Method (metoda fabrykująca)

Definiuje interfejs (metodę) tworzenia obiektu w klasie bazowej, ale pozwala podklasom decydować, jaką konkretną klasę instancjonować — odracza decyzję o konkretnym typie do podklasy.

abstract class Dokument {
    abstract Strona tworzStrone();   // metoda fabrykująca
    void otworz() {
        Strona s = tworzStrone();
        s.wyswietl();
    }
}
class DokumentTekstowy extends Dokument {
    Strona tworzStrone() { return new StronaTekstowa(); }
}

Zastosowanie: frameworki, gdzie biblioteka definiuje ogólny proces, a aplikacja kliencka dostarcza konkretne typy obiektów (np. różne typy dokumentów, różne typy połączeń sieciowych).

Prototype (prototyp)

Tworzy nowe obiekty przez klonowanie istniejącego obiektu-prototypu, zamiast budowania od zera — przydatne, gdy tworzenie obiektu jest kosztowne (np. wymaga odczytu z bazy/pliku), a nowy obiekt ma być tylko niewielką modyfikacją istniejącego.

interface Prototype { Prototype klonuj(); }
class Ksztalt implements Prototype {
    int x, y, kolor;
    Prototype klonuj() { return new Ksztalt(this.x, this.y, this.kolor); }
}

Zastosowanie: kopiowanie obiektów w grach (klonowanie wrogów/przedmiotów tego samego typu), obiekty z kosztowną inicjalizacją, patrz też przedmiot Programowanie obiektowe 2 — copy/deepcopy w Pythonie realizuje podobną ideę.

Singleton

Zapewnia, że klasa ma tylko jedną instancję w całej aplikacji, i udostępnia do niej globalny punkt dostępu — kontroluje liczbę instancji (zawsze dokładnie jedna), nie sposób ich tworzenia jak pozostałe wzorce kreacyjne.

class Konfiguracja {
    private static Konfiguracja instancja;
    private Konfiguracja() { /* prywatny konstruktor */ }

    public static Konfiguracja getInstance() {
        if (instancja == null) {
            instancja = new Konfiguracja();
        }
        return instancja;
    }
}

Zastosowanie: globalna konfiguracja aplikacji, pula połączeń do bazy danych, logger — obiekty, których z definicji powinna istnieć tylko jedna, współdzielona instancja.

Singleton bywa krytykowany jako "antywzorzec" przy nadużywaniu — wprowadza globalny, ukryty stan (utrudnia testowanie w izolacji, tworzy niejawne zależności między odległymi częściami kodu) — warto rozważyć wstrzykiwanie zależności (dependency injection) jako alternatywę.
Wspólny mianownik wzorców kreacyjnych: oddzielają proces tworzenia obiektu od kodu, który go używa — kod klienta zwykle nie musi znać konkretnej klasy tworzonego obiektu. Ułatwia to wymianę implementacji bez zmiany kodu korzystającego z obiektów.

4. Wzorce strukturalne

Adapter

"Tłumaczy" interfejs jednej klasy na interfejs, którego oczekuje kod klienta — pozwala współpracować klasom z niekompatybilnymi interfejsami, bez modyfikowania żadnej z nich (np. integracja starej/zewnętrznej biblioteki z nowym kodem).

interface NowyInterfejs { void dzialaj(); }
class StaraKlasa { void staraMetoda() { /*...*/ } }

class Adapter implements NowyInterfejs {
    StaraKlasa stara = new StaraKlasa();
    void dzialaj() { stara.staraMetoda(); }
}

Zastosowanie: integracja z zewnętrznymi API o innym kształcie niż oczekiwany, adaptacja starszych bibliotek do nowego kodu bez ich przepisywania.

Bridge (mostek)

Oddziela abstrakcję (interfejs "od strony klienta") od jej implementacji — tak, by obie strony (abstrakcja i implementacja) mogły się rozwijać/zmieniać niezależnie od siebie, unikając kombinatorycznej eksplozji klas przy wielu wariantach każdej strony.

interface Implementacja { void narysujKolo(); }
class ImplementacjaOpenGL implements Implementacja { void narysujKolo() { /*...*/ } }

abstract class Ksztalt {
    protected Implementacja impl;
    abstract void rysuj();
}
class Kolo extends Ksztalt {
    void rysuj() { impl.narysujKolo(); }
}

Zastosowanie: sterowniki graficzne wspierające wiele platform renderujących (OpenGL/DirectX) niezależnie od hierarchii kształtów, sterowniki bazodanowe wspierające wiele silników SQL.

Composite (kompozyt)

Komponuje obiekty w struktury drzewiaste typu "część-całość" i pozwala klientowi jednolicie traktować pojedyncze obiekty i ich grupy (kompozycje) przez wspólny interfejs.

interface Komponent { int rozmiar(); }
class Plik implements Komponent {
    int rozmiarBajtow;
    int rozmiar() { return rozmiarBajtow; }
}
class Folder implements Komponent {
    List<Komponent> dzieci = new ArrayList<>();
    int rozmiar() {
        int suma = 0;
        for (Komponent k : dzieci) suma += k.rozmiar();
        return suma;
    }
}

Zastosowanie: struktury plików/folderów, drzewo komponentów UI (kontener zawierający inne komponenty), struktura organizacyjna firmy (pracownik/menadżer z podwładnymi).

Decorator (dekorator)

Dynamicznie dodaje nowe zachowanie/odpowiedzialności do pojedynczego obiektu, "owijając" go inną klasą implementującą ten sam interfejs — elastyczniejsza alternatywa dla dziedziczenia, bo kombinacje "dekoracji" można łączyć w dowolnej kolejności w czasie działania.

interface Kawa { double cena(); }
class KawaZwykla implements Kawa { double cena() { return 5; } }

class ZMlekiem implements Kawa {
    Kawa opakowana;
    ZMlekiem(Kawa k) { opakowana = k; }
    double cena() { return opakowana.cena() + 2; }
}
// użycie: new ZMlekiem(new KawaZwykla()).cena()  → 7

Zastosowanie: strumienie I/O w Javie (BufferedReader owijający FileReader), dodawanie funkcji do obiektów UI (przewijanie, ramka), warstwy middleware.

Facade (fasada)

Zapewnia jeden, uproszczony interfejs do złożonego podsystemu (wielu współpracujących klas), ułatwiając jego użycie klientom, którzy nie muszą znać wewnętrznych szczegółów/zależności między tymi klasami.

class KinoDomoweFacade {
    Projektor projektor; Glosniki glosniki; Odtwarzacz odtwarzacz;
    void ogladajFilm() {
        projektor.wlacz();
        glosniki.ustawTryb("kino");
        odtwarzacz.odtworz();
    }
}

Zastosowanie: uproszczone API do złożonych bibliotek (np. jedna metoda inicjalizująca cały skomplikowany framework), warstwa "serwisów" ukrywająca szczegóły wielu repozytoriów/klas dostępu do danych.

Flyweight (waga piórkowa)

Redukuje zużycie pamięci przy bardzo dużej liczbie podobnych obiektów przez współdzielenie części ich stanu (stan wewnętrzny/intrinsic — wspólny dla wielu instancji, np. kształt litery), a przechowywanie tylko unikalnej części (stan zewnętrzny/extrinsic, np. pozycja) osobno dla każdej.

class Znak {   // flyweight — współdzielony dla wszystkich wystąpień tej samej litery
    char litera; Font font;
}
class PozycjaZnaku {  // stan zewnętrzny, unikalny per wystąpienie
    Znak znak; int x, y;
}

Zastosowanie: renderowanie tekstu (tysiące liter, ale tylko kilkadziesiąt unikalnych kształtów-glifów), obiekty w grach z tysiącami podobnych jednostek (drzewa w lesie, cząsteczki), edytory graficzne z dużą liczbą powtarzalnych elementów.

Proxy (pełnomocnik)

Obiekt zastępczy o tym samym interfejsie co obiekt docelowy, kontrolujący dostęp do niego — pośredniczy w wywołaniach, mogąc dodać logikę przed/po faktycznym wywołaniu (kontrola dostępu, leniwe ładowanie, logowanie, cache).

interface Obraz { void wyswietl(); }
class ObrazRzeczywisty implements Obraz {
    ObrazRzeczywisty(String plik) { wczytajZDysku(plik); }  // kosztowne
    void wyswietl() { /*...*/ }
}
class ObrazProxy implements Obraz {
    String plik; ObrazRzeczywisty rzeczywisty;
    void wyswietl() {
        if (rzeczywisty == null) rzeczywisty = new ObrazRzeczywisty(plik);  // leniwe tworzenie
        rzeczywisty.wyswietl();
    }
}

Zastosowanie: leniwe ładowanie (lazy loading) kosztownych zasobów, proxy zdalne (obiekt lokalny reprezentujący usługę sieciową — patrz komunikacja klient-serwer), proxy zabezpieczające (sprawdzanie uprawnień przed faktycznym wywołaniem), reverse proxy na poziomie sieci (patrz przedmiot Administracja serwerami WWW — to ta sama idea, na poziomie infrastruktury).

Wspólny mianownik wzorców strukturalnych: dotyczą jak klasy/obiekty są komponowane w większe struktury, zachowując elastyczność i wydajność systemu — w odróżnieniu od tworzenia obiektów (kreacyjne) czy sposobów ich interakcji w czasie (behawioralne).

5. Wzorce architektoniczne

W odróżnieniu od wzorców GoF (poziom pojedynczych klas/obiektów), wzorce architektoniczne operują na wyższym poziomie — organizują całą strukturę aplikacji/systemu.

MVC (Model-View-Controller)

Rozdzielenie danych/logiki biznesowej (Model), prezentacji (View) i obsługi żądań/koordynacji (Controller) — patrz przedmiot Bazy danych w aplikacjach internetowych po pełny opis. Kontroler odbiera żądanie, woła Model, przekazuje dane do View, View generuje odpowiedź.

MVP (Model-View-Presenter)

Wariant MVC, w którym Presenter przejmuje więcej logiki prezentacji z widoku — widok jest "cienki" (pasywny), zawiera minimum logiki, praktycznie tylko wyświetla to, co każe mu Presenter — ułatwia to testowanie logiki prezentacji w izolacji od faktycznego UI (widok można łatwo zamockować).

MVVM (Model-View-ViewModel)

Wariant popularny w aplikacjach z dwustronnym wiązaniem danych (data binding, np. Angular, WPF) — ViewModel eksponuje dane i komendy w formie, którą widok automatycznie "obserwuje" i synchronizuje się z nią, bez ręcznego, jawnego "przepisywania" wartości między warstwami (jak trzeba by robić w klasycznym MVC/MVP).

Architektura warstwowa (Layered / N-tier)

Podział systemu na poziome warstwy (typowo: prezentacja → logika biznesowa → dostęp do danych), gdzie każda warstwa komunikuje się tylko z warstwami bezpośrednio sąsiednimi — zmiana w jednej warstwie (np. zmiana bazy danych) nie powinna wymagać zmian w warstwach odległych (np. UI), o ile interfejs między warstwami pozostaje stabilny.

Mikroserwisy

System podzielony na małe, niezależnie wdrażane serwisy, komunikujące się przez sieć (REST, komunikaty asynchroniczne) — patrz przedmioty Projektowanie aplikacji internetowych i Technologie DevOps po pełny opis, w tym porównanie z architekturą monolityczną.

Event-Driven Architecture (architektura sterowana zdarzeniami)

Komponenty komunikują się przez publikowanie/nasłuchiwanie zdarzeń, zamiast bezpośrednich wywołań metod — silne odsprzęglenie: nadawca zdarzenia nie musi wiedzieć, kto (i ile komponentów) je odbiera. Bezpośrednio realizuje na poziomie architektury tę samą ideę, co wzorzec Observer na poziomie obiektów (patrz punkt 2). Praktyczna implementacja: brokery komunikatów jak RabbitMQ (patrz przedmiot Programowanie sieciowe).

Architektura klient-serwer

Podział na komponent żądający usług (klient) i dostarczający je (serwer) — fundamentalny podział większości aplikacji sieciowych (patrz przedmioty Sieci komputerowe, Programowanie sieciowe). Serwer skupia logikę/dane, klient (przeglądarka, aplikacja mobilna) prezentuje interfejs i wysyła żądania.

Potok-filtr (Pipe-and-Filter)

Dane przepływają przez sekwencję niezależnych, wymiennych "filtrów", z których każdy przetwarza dane i przekazuje wynik do następnego w łańcuchu (potoku) — analogia do potoków powłoki systemowej (patrz przedmiot Wprowadzenie do systemów operacyjnych, komenda |). Każdy filtr można rozwijać/testować/wymieniać niezależnie od pozostałych.

Różnica poziomu abstrakcji: wzorce GoF (punkty 2-4) rozwiązują lokalne problemy projektowe w kodzie (relacje między kilkoma klasami); wzorce architektoniczne definiują globalną strukturę całej aplikacji/systemu — oba poziomy zwykle współistnieją w jednym projekcie (np. aplikacja w architekturze MVC, gdzie wewnątrz kontrolerów/modeli używane są wzorce Strategy, Factory Method, Observer itd.).
