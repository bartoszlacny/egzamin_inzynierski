Bazy danych w aplikacjach internetowych

1. Procedury składowe, funkcje, wyzwalacze

Procedura składowa (stored procedure)

Blok kodu SQL zapisany i przechowywany w bazie danych, wywoływany po nazwie — pozwala przenieść część logiki (nie tylko surowe zapytania) bliżej danych, na serwer bazy.

CREATE PROCEDURE DodajZamowienie(IN p_klient INT, IN p_produkt VARCHAR(50), IN p_cena DECIMAL(10,2))
BEGIN
    INSERT INTO Zamowienie (id_klient, produkt, cena) VALUES (p_klient, p_produkt, p_cena);
    UPDATE Klient SET liczba_zamowien = liczba_zamowien + 1 WHERE id = p_klient;
END;

CALL DodajZamowienie(1, 'Laptop', 3500.00);

Funkcja składowana

Podobna do procedury, ale zawsze zwraca wartość i można ją użyć wewnątrz zapytania SQL (tam, gdzie procedury nie można):

CREATE FUNCTION SumaZamowien(p_klient INT) RETURNS DECIMAL(10,2)
BEGIN
    DECLARE suma DECIMAL(10,2);
    SELECT SUM(cena) INTO suma FROM Zamowienie WHERE id_klient = p_klient;
    RETURN suma;
END;

SELECT nazwa, SumaZamowien(id) AS suma FROM Klient;

Wyzwalacz (trigger)

Blok kodu wykonywany automatycznie w reakcji na zdarzenie w tabeli (INSERT, UPDATE, DELETE) — bez konieczności jawnego wywołania.

CREATE TRIGGER PoZamowieniu
AFTER INSERT ON Zamowienie
FOR EACH ROW
BEGIN
    UPDATE Produkt SET stan_magazynu = stan_magazynu - 1 WHERE nazwa = NEW.produkt;
END;
MomentBEFOREAFTER
Zdarzenieprzed zapisaniem zmiany — można ją jeszcze zmodyfikować/odrzucićpo zapisaniu zmiany — do reakcji "skutkowej" (np. aktualizacja innej tabeli)

NEW — nowe wartości wiersza (dla INSERT/UPDATE); OLD — poprzednie wartości (dla UPDATE/DELETE).

Typowe zastosowanie triggerów: automatyczne logowanie historii zmian (audit log), wymuszanie reguł biznesowych niezależnie od tego, czy zmiana pochodzi z aplikacji webowej czy z bezpośredniego zapytania administratora.

2. Transakcje

(pełny opis własności ACID i poziomów izolacji — patrz przedmiot Relacyjne bazy danych; tu skrócenie + kontekst aplikacji webowej)

Transakcje w kontekście aplikacji webowej

BEGIN TRANSACTION;
UPDATE Konto SET saldo = saldo - 100 WHERE id = 1;
UPDATE Konto SET saldo = saldo + 100 WHERE id = 2;
COMMIT;

W typowej aplikacji webowej transakcja zwykle odpowiada jednej operacji biznesowej zainicjowanej przez użytkownika (np. "złóż zamówienie" — zapis zamówienia + aktualizacja stanu magazynu + ewentualne obciążenie płatności — wszystko musi się powiodło razem, albo nic).

Transakcje a połączenia z bazą (connection pooling)

Aplikacje webowe zwykle korzystają z puli połączeń (connection pool) do bazy danych — transakcja jest związana z konkretnym połączeniem, więc framework/ORM musi zapewnić, że wszystkie zapytania danej transakcji idą przez to samo połączenie.

Typowy wzorzec w kodzie backendu

try:
    conn.begin()
    conn.execute("UPDATE Konto SET saldo = saldo - 100 WHERE id = 1")
    conn.execute("UPDATE Konto SET saldo = saldo + 100 WHERE id = 2")
    conn.commit()
except Exception as e:
    conn.rollback()
    raise e

Transakcje rozproszone (skrótowo)

Gdy operacja biznesowa obejmuje wiele niezależnych systemów/baz danych (np. mikroserwisy — patrz przedmiot Projektowanie aplikacji internetowych), klasyczna transakcja ACID nie wystarcza — stosuje się wzorce jak Saga (sekwencja lokalnych transakcji z akcjami kompensującymi w razie błędu) zamiast jednej, globalnej transakcji.

Typowe pytanie: dla scenariusza "rezerwacja lotu + płatność" wskaż, dlaczego te dwie operacje powinny (lub w architekturze mikroserwisowej: nie mogą łatwo) być jedną transakcją ACID, i jak inaczej zapewnić spójność.

3. Wzorzec MVC (Model-View-Controller)

Wzorzec architektoniczny rozdzielający aplikację na trzy niezależne warstwy odpowiedzialności — szczególnie istotny w aplikacjach z bazą danych, bo jasno określa, gdzie powinna żyć logika dostępu do danych.

WarstwaOdpowiedzialnośćPrzykład
Model dane i logika biznesowa — komunikacja z bazą danych, walidacja, reguły domenowe klasa Zamowienie z metodami do zapisu/odczytu z bazy
View (widok) prezentacja danych użytkownikowi — HTML/szablon, bez logiki biznesowej szablon strony wyświetlający listę zamówień
Controller (kontroler) odbiera żądania użytkownika, koordynuje Model i View — "dyrygent" funkcja obsługująca żądanie HTTP POST /zamowienia

Przepływ żądania w MVC

Żądanie HTTP → Controller → (odczyt/zapis) → Model → baza danych
                    ↓
                  View → wygenerowana odpowiedź HTML/JSON → użytkownik

Dlaczego MVC pomaga przy bazach danych

  • logika SQL/ORM jest izolowana w Modelu — nie rozsiana po całym kodzie (kontrolerach, widokach), co ułatwia zmianę bazy danych albo refaktoryzację
  • Kontroler nie zawiera bezpośrednio zapytań SQL — tylko woła metody Modelu (np. Zamowienie.znajdzPoId(5)), co ułatwia testowanie (można "podłożyć" fałszywy Model w testach)
  • View nie ma dostępu do bazy — otrzymuje już przygotowane dane od Kontrolera, co zapobiega przypadkowemu wstrzykiwaniu logiki biznesowej do szablonów

Warianty i pokrewne wzorce

MVVM (Model-View-ViewModel — częste w aplikacjach frontendowych/desktopowych), MVP (Model-View-Presenter) — różne rozłożenie odpowiedzialności między "pośrednikiem" a widokiem, ale ta sama idea rozdzielenia danych/logiki od prezentacji.

Typowe pytanie: dla podanego (złego) fragmentu kodu z zapytaniem SQL wklejonym prosto w szablon HTML, wskaż naruszenie zasad MVC i zaproponuj poprawną strukturę (przeniesienie zapytania do Modelu).

4. Projektowanie baz danych dla aplikacji webowych

Specyfika projektowania dla web (względem "ogólnego" projektowania z RBD)

  • skalowalność odczytu — aplikacje webowe zwykle mają znacznie więcej odczytów niż zapisów (read-heavy) — warto przewidzieć indeksy (patrz przedmiot Relacyjne bazy danych) na kolumnach filtrowanych przy typowych żądaniach stron
  • sesje użytkowników — tabela/mechanizm przechowywania stanu sesji (albo zewnętrzny magazyn jak Redis, zamiast bazy relacyjnej, dla wydajności)
  • dane "miękko" usuwane (soft delete) — zamiast DELETE, często oznacza się wiersz jako usunięty (flaga usunieto = true) — zachowuje historię, ułatwia "przywracanie", ale wymaga pamiętać o filtrowaniu takich wierszy we wszystkich zapytaniach

ORM (Object-Relational Mapping)

Warstwa mapująca wiersze tabel na obiekty w kodzie aplikacji (i odwrotnie) — programista operuje na obiektach/klasach, a ORM generuje odpowiednie zapytania SQL "pod maską".

# przykład koncepcyjny (styl Django/SQLAlchemy)
klient = Klient.objects.get(id=5)
klient.email = "nowy@example.com"
klient.save()          # ORM generuje UPDATE ... WHERE id=5
Zalety ORMWady ORM
mniej ręcznie pisanego SQL, bezpieczniejsze domyślnie (chroni przed SQL injection)mniejsza kontrola nad wygenerowanym zapytaniem — czasem nieoptymalne
przenośność między różnymi bazami danych (ORM "tłumaczy" różnice składniowe)problem N+1 — nieuważne użycie może generować masę osobnych zapytań tam, gdzie jedno złączenie (JOIN) by wystarczyło

Migracje bazy danych

Wersjonowane, uporządkowane zmiany struktury bazy danych (dodanie kolumny, nowej tabeli) — pozwalają zespołowi śledzić historię zmian schematu (podobnie jak Git dla kodu) i odtworzyć/zaktualizować strukturę bazy na każdym środowisku (dev/test/produkcja) w tej samej, znanej kolejności.

Cache'owanie zapytań

Wyniki często powtarzanych, kosztownych zapytań (np. lista popularnych produktów) przechowywane tymczasowo w szybszej pamięci (Redis, Memcached) — zmniejsza obciążenie bazy głównej przy dużym ruchu, kosztem ryzyka "nieaktualnych" danych (trzeba świadomie zarządzać unieważnianiem cache przy zmianie danych).

Typowe pytanie: zaprojektuj schemat bazy dla prostego systemu blogowego (użytkownicy, posty, komentarze) z uwzględnieniem typowych potrzeb aplikacji webowej — indeksy na kolumnach często filtrowanych (np. data publikacji), rozważenie soft delete dla komentarzy.

5. Bezpieczeństwo baz danych w aplikacjach webowych

SQL Injection (przypomnienie z Języków hipertekstowych)

Wstrzyknięcie złośliwego kodu SQL przez niesprawdzone dane wejściowe — podstawowa ochrona to zapytania przygotowane (prepared statements) lub użycie ORM (patrz punkt 4), nigdy bezpośrednie wklejanie danych użytkownika do zapytania SQL jako tekstu.

# NIEBEZPIECZNE
query = f"SELECT * FROM Uzytkownicy WHERE login = '{login}'"

# BEZPIECZNE — zapytanie przygotowane
query = "SELECT * FROM Uzytkownicy WHERE login = %s"
cursor.execute(query, (login,))

Zasada najmniejszych uprawnień (least privilege)

Konto bazy danych używane przez aplikację webową powinno mieć tylko uprawnienia faktycznie potrzebne (np. SELECT/INSERT/UPDATE na konkretnych tabelach) — nigdy uprawnienia administratora bazy. W razie włamania przez inną podatność (np. SQL injection, którego jakoś nie wychwycono), ograniczone uprawnienia konta minimalizują potencjalne szkody.

Szyfrowanie danych wrażliwych

  • hasła — nigdy w postaci czystego tekstu; hashowanie (bcrypt, Argon2) z solą (salt) — nawet wyciek bazy nie odkrywa hasła (patrz przedmiot Projektowanie aplikacji internetowych)
  • inne dane wrażliwe (numery kart, dane osobowe) — szyfrowanie "w spoczynku" (encryption at rest) na poziomie kolumny lub całej bazy

Backup i disaster recovery

Regularne, zautomatyzowane kopie zapasowe bazy danych (patrz przedmiot Administracja i integracja systemów operacyjnych — automatyzacja przez cron/systemd timers) — testowane pod kątem faktycznej możliwości odtworzenia (backup, którego nikt nigdy nie próbował przywrócić, to backup tylko "w teorii").

Audyt i logowanie

Rejestrowanie, kto i kiedy dokonał istotnych zmian w danych (np. przez trigery z punktu 1, albo dedykowane mechanizmy audytu bazy) — pomaga wykryć nieautoryzowany dostęp i spełnić wymogi regulacyjne (patrz RODO — przedmiot Projektowanie aplikacji internetowych).

Izolacja środowisk

Baza produkcyjna (z realnymi danymi użytkowników) powinna być odseparowana od środowisk deweloperskich/testowych — dane testowe/deweloperskie powinny być zanonimizowane lub sztucznie wygenerowane, nie kopią rzeczywistych, wrażliwych danych klientów.

Typowe pytanie: dla opisanego kodu backendu z widoczną podatnością (np. konkatenacja stringów w zapytaniu SQL, hasła zapisywane jako plaintext) wskaż wszystkie problemy bezpieczeństwa i zaproponuj poprawki zgodne z dobrymi praktykami.
